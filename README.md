# Zond

Консольный статический анализатор Java-кода. Проверяет исходники, файлы настроек Spring-приложения,
миграции БД, файлы сборки, Docker, Kubernetes, CI и настройки логирования по набору правил (сейчас их 454) и выводит найденные проблемы в консоль, текстовый файл или Excel.

Работает без базы данных и внешних сервисов: на входе папка с кодом, на выходе отчет.

## Сборка

Нужна Java 21. Gradle ставить не надо — он скачается оберткой.

```bash
./gradlew build
```

Готовое приложение: `build/libs/zond-0.0.1-SNAPSHOT.jar`.

## Запуск

### С меню

```bash
java -jar build/libs/zond-0.0.1-SNAPSHOT.jar
```

Без пути в аргументах приложение показывает список папок текущей директории, предлагает выбрать ту,
которую нужно проверить, и открывает меню:

```
Главное меню
  1. Сканировать (C:\projects\shop)
  2. Выбрать другую папку
  3. Настройки
  4. Список правил
  5. Выход
```

- **Выбор папки.** Номер открывает папку, `0` выбирает показанную, `1` поднимает на уровень выше.
  Путь можно ввести и вручную, в том числе к отдельному `.java`-файлу. Пустая строка — отмена.
- **Настройки.** Папка и формат отчета, сканирование тестов, минимальный уровень и уверенность,
  отключенные правила, исключенные пути, виды файлов помимо Java, единица времени, число потоков,
  проверка только измененных файлов. Неверный ввод (число потоков не от 0 до 128, имя ветки с пробелом)
  не принимается: меню объясняет, что не так, и спрашивает заново.
  Каждое изменение сразу записывается в `app.properties`.
- **Список правил.** Показывает правила с кодами, уровнями и описаниями либо выгружает их в
  `zond-rules.txt` / `zond-rules.xlsx`.

### Без меню: для скриптов и CI

```bash
java -jar build/libs/zond-0.0.1-SNAPSHOT.jar --path=/projects/shop --report=reports/shop.xlsx
```

С путем в аргументах приложение сканирует, пишет отчет и завершается.

| Код завершения | Что значит |
|---|---|
| 0 | проблем не найдено |
| 1 | проблемы найдены |
| 2 | сканирование не состоялось: нет такого пути, ошибка в настройках |

## Аргументы командной строки

| Аргумент | Что делает |
|---|---|
| `--version` | Показать версию zond и выйти. |
| `--path=<путь>` | Что проверять: папка или `.java`-файл. Можно передать и просто первым аргументом без имени. |
| `--report=<файл>` | Куда писать отчет. Формат задает расширение: `.xlsx` — Excel, `.html` — веб-страница, `.sarif` — SARIF, любое другое — текст. Без аргумента и без настройки отчет выводится в консоль. |
| `--min-level=<уровень>` | В отчет попадают проблемы этого уровня и строже: `CRITICAL`, `MAJOR`, `MINOR`, `INFO`. |
| `--min-confidence=<уверенность>` | В отчет попадают находки с этой уверенностью и выше: `CONFIRMED`, `PROBABLE`, `SUSPICION`. См. [Уверенность находки](#уверенность-находки). |
| `--zond.progress.percent=false` | Не показывать процент в ходе сканирования. |
| `--statistic-report=<файл.xlsx>` | Выгрузить статистику по правилам: время работы и число замечаний. См. [Статистика по правилам](#статистика-по-правилам). |
| `--time-unit=<единица>` | В чем показывать время работы правил и всей проверки: `ms` — миллисекунды, `s` — секунды. |
| `--zond.report.confidence=false` | Не показывать уверенность находок в отчете. |
| `--disable=<правила>` | Правила, которые не запускать: коды или имена через запятую (`jr:40,TodoCommentRule`). Добавляются к отключенным в настройках. |
| `--changed-only` | Показывать находки только в измененных файлах: в репозитории git их называет git, в остальных папках они ищутся по хешам. `--changed-only=false` отменяет режим, заданный в настройках. См. [Только измененные файлы](#только-измененные-файлы). |
| `--changed-since=<ветка>` | С чем сравнивать в репозитории git: ветка, тег или коммит (`origin/main`, `v1.2.0`, `HEAD~3`). Сам включает режим `--changed-only`. |
| `--skip-tests` | Не проверять файлы из каталогов `test`. `--skip-tests=false` отменяет пропуск, заданный в настройках. |
| `--classpath=<пути>` | Библиотеки проверяемого проекта: jar-файлы или папки с ними через `;`. См. [Разрешение типов](#разрешение-типов). |
| `--auto-classpath=false` | Не искать библиотеки проекта по его `pom.xml`. См. [Разрешение типов](#разрешение-типов). |
| `--exclude=<шаблоны>` | Пути, которые не нужно сканировать, через запятую. Добавляются к заданным в настройках. См. [Исключение путей](#исключение-путей). |
| `--threads=<число>` | Число потоков сканирования: `1` — в один поток, `0` — по числу ядер процессора. См. [Параллельное сканирование](#параллельное-сканирование). |
| `--scan-sql`, `--scan-build-files`, `--scan-docker`, `--scan-config`, `--scan-messages`, `--scan-logging`, `--scan-kubernetes`, `--scan-ci` | Проверять ли этот вид файлов: `--scan-sql=false` отключает. См. [Что проверяется кроме Java](#что-проверяется-кроме-java). |
| `--zond.max-call-depth=<число>` | Глубина поиска по вызовам для всех правил, у которых она есть. |
| `--config=<файл>` | Файл настроек вместо `./app.properties`. |
| `--zond.rule.<правило>.<параметр>=<значение>` | Порог или уровень отдельного правила. См. [Настройка отдельных правил](#настройка-отдельных-правил). |

Аргумент всегда важнее той же настройки из файла.

## Версия

Версия задается в одном месте — строкой `version` в `build.gradle` — и при сборке попадает в приложение.
Она видна:

- в баннере при запуске и в заголовке главного меню;
- по аргументу `--version`: печатается строка вида `Zond 0.0.1-SNAPSHOT`, сканирование не запускается;
- в каждом отчете: строка «Версия Zond» в текстовом, HTML и Excel, поле `tool.driver.version` в SARIF.
  По ней видно, какой версией получен отчет: набор правил от версии к версии меняется.

При запуске из среды разработки без сборки Gradle вместо версии показывается `dev`.

Номер версии — `MAJOR.MINOR.PATCH`: исправления ложных срабатываний и ошибок повышают `PATCH`; новые
правила, настройки и форматы отчета — `MINOR`; удаленные или переименованные настройки и правила,
измененные коды `jr:N` — `MAJOR`.

## Время работы

В ходе сканирования рядом с каждым правилом показывается, сколько оно работало, а после отчета —
сколько заняла вся проверка:

```
[  1 / 422]    0%  TransactionOnPrivateMethodRule (jr:1)             14 мс
[  2 / 422]    0%  SelfInvocationRule (jr:2)                        231 мс
...
Затраченное время: 12480 мс
```

Единица задается свойством `zond.progress.time-unit` (`ms` или `s`), аргументом `--time-unit=...` и пунктом
«Единица времени» в настройках меню. В секундах время идет с долями: `0.014 с`, `12.480 с`.

- Общее время отсчитывается от запуска первого правила до конца последнего. Поиск библиотек проекта,
  загрузка и разбор кода, запись отчета в него не входят.
- В один поток строка правила появляется, когда оно начинает работать, а время дописывается в конце:
  видно, какое правило выполняется сейчас. В несколько потоков (`zond.scan.threads`) правило печатается,
  когда закончилось, и общее время меньше суммы по правилам: они работают одновременно.

### Статистика по правилам

Помимо основного отчета можно выгрузить файл Excel со статистикой: сколько каждое правило работало
и сколько замечаний нашло.

```properties
zond.report.statistic.path=zond-statistic.xlsx
zond.report.statistic.red-percent=10
zond.report.statistic.yellow-percent=3
zond.report.statistic.green-percent=0
```

Файл задается и аргументом `--statistic-report=zond-statistic.xlsx`. Пока путь не задан, статистика не пишется.

| Колонка | Что в ней |
|---|---|
| Правило | Имя и код правила. |
| Время работы | В единице из `zond.progress.time-unit`: целые миллисекунды либо секунды с долями. |
| Доля от общего времени, % | Время правила относительно суммы времени всех правил. |
| Найдено замечаний | Сколько находок правила попало в отчет. |
| Доля от всех замечаний, % | Находки правила относительно общего числа найденных проблем. |

- Самые медленные правила идут первыми. Строка «Всего» — сумма по всем правилам, 100 %. По любой колонке
  таблицу можно пересортировать фильтром Excel.
- Замечания считаются все вместе, без деления по уровням: `CRITICAL`, `MAJOR`, `MINOR` и `INFO` идут в одно
  число. Это те же находки, что в основном отчете: скрытые `zond:ignore`, порогом уровня или уверенности
  не учитываются. Правило без находок остается в таблице с нулем.
- Число замечаний и их доля подсвечены зеленым, если правило нашло хотя бы одно замечание. Строка «Всего»
  не подсвечивается.
- Цвет первых трех колонок относится ко времени: закрашиваются правило, его время и доля времени. Красным — от
  `red-percent`, желтым — от `yellow-percent`, зеленым — от `green-percent`. Правило получает самый тяжелый
  цвет, порога которого достигло. С порогом зеленого `0` зеленые все, кто не дотянул до желтого.
- Пороги — числа от 0 до 100, по убыванию: красный не меньше желтого, желтый не меньше зеленого. Иначе
  приложение завершится с кодом 2.
- Доли времени в сумме всегда дают 100 %: они считаются от суммы времени всех правил. Загрузка и разбор
  кода в это время не входят.
- Под строкой «Всего» стоит «Время проверки» — то же число, что печатается в консоли: от запуска первого
  правила до конца последнего. В один поток оно почти равно сумме, в несколько — меньше ее: правила
  работают одновременно.
- Под таблицей записаны пороги, с которыми построена статистика, и версия Zond.
- Статистика пишется только в Excel: имя файла должно заканчиваться на `.xlsx`.

## Настройки: app.properties

Файл `app.properties` читается из папки, в которой запущено приложение (или из `--config`).
Он необязателен, кодировка — UTF-8.

| Свойство | По умолчанию | Что задает |
|---|---|---|
| `zond.report.path` | пусто — консоль | Файл отчета. Формат определяется расширением. |
| `zond.rules.disabled` | пусто | Отключенные правила: коды или имена через запятую. |
| `zond.rules.min-level` | `INFO` | Наименее строгий уровень, который попадает в отчет. |
| `zond.rules.min-confidence` | `SUSPICION` | Наименьшая уверенность находки, с которой она попадает в отчет. |
| `zond.progress.percent` | `true` | Показывать процент рядом со счетчиком правил при сканировании. |
| `zond.progress.time-unit` | `ms` | В чем показывать время работы правил и всей проверки: `ms` — миллисекунды, `s` — секунды. См. [Время работы](#время-работы). |
| `zond.report.statistic.path` | пусто — не выгружать | Файл `.xlsx` для статистики по правилам: время работы и число замечаний. |
| `zond.report.statistic.red-percent` | `10` | Доля правила в общем времени, с которой его время в статистике красное. |
| `zond.report.statistic.yellow-percent` | `3` | То же для желтого. |
| `zond.report.statistic.green-percent` | `0` | То же для зеленого; правило с меньшей долей остается без цвета. |
| `zond.report.confidence` | `true` | Показывать уверенность находок в отчете. |
| `zond.scan.skip-tests` | `false` | Не проверять каталоги `test`. |
| `zond.scan.changed-only` | `false` | Показывать находки только в измененных файлах. См. [Только измененные файлы](#только-измененные-файлы). |
| `zond.scan.changed-since` | пусто — `HEAD` | С чем сравнивать рабочую копию git: ветка, тег или коммит. Пусто — только незакоммиченные изменения. Вне репозитория git не используется. |
| `zond.scan.snapshot-dir` | `~/.zond/snapshots` | Где хранить хеши файлов, по которым ищутся изменения в папке без git. |
| `zond.scan.test-rules-only` | `true` | В каталогах `test` работают только правила для тестов. См. [Тесты и код приложения](#тесты-и-код-приложения). |
| `zond.scan.classpath` | пусто | Библиотеки проверяемого проекта для разрешения типов. |
| `zond.scan.auto-classpath` | `true` | Искать библиотеки проекта самому: по его `pom.xml` в локальном репозитории Maven. |
| `zond.scan.maven-repository` | `~/.m2/repository` | Локальный репозиторий Maven, если он лежит в другом месте. |
| `zond.scan.exclude` | пусто | Пути, которые не нужно сканировать: шаблоны через запятую. |
| `zond.scan.threads` | `1` | Число потоков сканирования от 0 до 128: `1` — в один поток, `0` — по числу ядер. |
| `zond.scan.sql`, `zond.scan.build-files`, `zond.scan.docker`, `zond.scan.config`, `zond.scan.messages`, `zond.scan.logging`, `zond.scan.kubernetes`, `zond.scan.ci` | `true` | Проверять ли этот вид файлов помимо Java. |
| `zond.max-call-depth` | у каждого правила свое: от 3 до 6 | Глубина поиска по вызовам сразу для всех правил, у которых она есть. См. [Глубина поиска по вызовам](#глубина-поиска-по-вызовам). |
| `zond.flow.library` | пусто | Свой справочник методов библиотек для анализа потока данных; дополняет встроенный. |
| `zond.rule.<правило>.<параметр>` | — | Пороги и уровень отдельных правил. |

Пример:

```properties
zond.report.path=reports/zond-report.xlsx
zond.rules.disabled=jr:40, TodoCommentRule
zond.rules.min-level=MAJOR
zond.scan.skip-tests=true
```

## Отчет

Каждая находка содержит уровень, тип, уверенность, код правила, файл, строку и объяснение, что не так и как
исправить:

```
[CRITICAL] [LOGICAL] [jr:1] src\main\java\shop\OrderService.java:42 - @Transactional над приватным методом ...
```

Уровни от самого строгого: `CRITICAL`, `MAJOR`, `MINOR`, `INFO`.

В Excel-отчете три листа: «Сводка» (числа по уровням и правилам), «Проблемы» (все находки с фильтром
по любой колонке) и «Не разобраны» (файлы, которые не удалось прочитать как Java-код).

HTML-отчет — одна самодостаточная страница: сводка, находки по файлам, переключатели уровней, отбор
по типу правила и поиск по файлу, коду правила и тексту. Кнопки типов («Производительность»,
«Безопасность», «Логические ошибки» и другие, с числом находок) работают так: пока ни одна не нажата,
показываются все типы; нажатые сужают список до своих типов, «Все» сбрасывает отбор. Отбор по типу
сочетается с уровнями и поиском. Страницу можно переслать или приложить к сборке.

SARIF (версия 2.1.0) понимают GitHub Code Scanning, GitLab, Azure DevOps и IDE: находки показываются
прямо в коде и в pull request. `CRITICAL` передается как `error`, `MAJOR` — как `warning`,
остальные — как `note`; пути записаны от корня сканирования.

Помимо `.java`-файлов проверяются файлы настроек Spring, SQL-миграции, файлы сборки и Dockerfile —
см. [Что проверяется кроме Java](#что-проверяется-кроме-java).

## Уверенность находки

Уровень говорит, насколько плоха проблема, если она есть. Уверенность — есть ли она на самом деле.

| Уверенность | Что означает | Примеры |
|---|---|---|
| `CONFIRMED` — подтверждено | установлено по коду | данные запроса прослежены до SQL-запроса; переменная в этой точке всегда `null`; метод длиннее порога; проверка SSL отключена без условия |
| `PROBABLE` — вероятно | похоже на проблему, но часть условий по коду проверить нельзя | значение `null` на одном из путей; в запрос попадает сообщение из очереди или ответ другого сервиса |
| `SUSPICION` — подозрение | совпадение по имени или шаблону | поле названо `token`; используется `MD5`, а для чего — не видно; опасное место найдено, а источник данных нет |

Уверенность показывается в каждой находке и сводкой в шапке отчета:

```
Найдено проблем: 801
По уверенности: подтверждено: 402, вероятно: 377, подозрение: 22
```

Чтобы оставить в отчете только то, в чем анализатор уверен:

```properties
zond.rules.min-confidence=CONFIRMED
```

То же задается аргументом `--min-confidence=...` и пунктом «Минимальная уверенность» в настройках меню.
Число скрытых находок выводится в шапке отчета.

Вывод уверенности отключается настройкой:

```properties
zond.report.confidence=false
```

Тогда из отчета пропадают пометка в каждой находке, сводка в шапке, колонка в Excel и поле в SARIF.
На отбор находок это не влияет: `zond.rules.min-confidence` продолжает действовать, и число скрытых
находок по-прежнему выводится.

Как назначается уверенность:

- **Находка с отслеживанием данных** получает уверенность по источнику: запрос клиента и загруженный
  файл — подтверждено; сообщение из очереди, ответ внешнего сервиса, значение, прошедшее через свойство
  объекта, — вероятно; источник не найден — подозрение.
- **Правила потока данных:** «всегда `null`», «условие всегда истинно», недостижимый код, деление на
  ноль и обращение к пустому `Optional` — подтверждено; «может быть `null`» — вероятно. Передача в метод
  литерала `null` — подтверждено, значения, которое лишь может быть `null`, — вероятно.
- **Правила с цепочками вызовов** (jr:8, jr:57, jr:58, jr:63, jr:427): если каждый вызов в цепочке найден
  разрешением типов — подтверждено; если хотя бы один сопоставлен с методом по имени — вероятно.
  Обращение к репозиторию прямо в цикле — подтверждено.
- **Замечания о качестве кода** — подтверждено: это факт, видный в тексте.
- **Правила, которые судят по имени** (секрет в `toString()`, сравнение секретов, слабый хеш, `Random`) —
  подозрение.
- **Остальные правила** — вероятно.

У правил, которые не прослеживают данные и не строят цепочек, уверенность по-прежнему одна на все находки.

Значение — только `true` или `false`, любое другое останавливает запуск с кодом 2. То же переключается
пунктом «Файлы помимо Java» в настройках меню.

Что стоит знать:

- Сверка кода с настройками (jr:301, jr:302) работает по строкам из кода: `@Value("${...}")`,
  `@ConfigurationProperties`, `@ConditionalOnProperty`, `getProperty(...)`. Свойство, которое читает
  подключенная библиотека, а не ваш код, будет названо неиспользуемым — такую находку скройте
  комментарием `# zond:ignore jr:302`. Свойства самого Spring и распространенных библиотек (`spring.*`, `server.*`,
  `logging.*`, `management.*` и подобные) не проверяются.
- Свойство с переменной окружения (`${DB_HOST}` заглавными буквами) и со значением по умолчанию
  (`${app.limit:5}`) пропущенным не считается.
- **Как разбираются файлы.** YAML читает SnakeYAML, XML — потоковый парсер из JDK: списки, многострочные
  блоки, кавычки и комментарии понимаются так же, как их понимает само приложение. Элемент списка в
  настройках получает ключ с индексом, как в Spring: `app.servers[0].host`. Файл, который корректным
  YAML не является (подстановка сборки `@project.version@`, шаблон Helm), читается построчно, если это
  настройки Spring, и пропускается в остальных случаях.
- **Журналы Liquibase** узнаются по корневому элементу `databaseChangeLog`, имя файла может быть любым.
  Каждое изменение (`createTable`, `addColumn`, `dropColumn`, `dropTable`, `createIndex`,
  `addForeignKeyConstraint`, `renameColumn`, `renameTable`, `modifyDataType`, `addNotNullConstraint`,
  `update`, `delete`, `sql` и другие) переводится в равнозначную команду SQL
  и проверяется теми же правилами jr:290 – jr:293. Блок `rollback` не проверяется: он выполняется,
  только когда миграцию отменяют.
- **Версии в `pom.xml`.** `${...}` заменяется значением из `<properties>` самого файла и родительских
  `pom.xml` (по `<relativePath>`, по умолчанию `../pom.xml`), `${project.version}` — версией модуля.
  Родитель, которого нет среди проверяемых файлов (например, `spring-boot-starter-parent`), не читается,
  и версия остается неизвестной. Зависимости плагинов сборки не проверяются. В `build.gradle`
  читаются только строки вида `implementation 'group:artifact:version'`: это программа, а не описание.
- **Настройки логирования для тестов** (`logback-test.xml`, все из каталогов `test`) не проверяются.
  Уровень корневого логгера (jr:307) не проверяется и внутри `<springProfile>` с профилями `dev`,
  `local`, `test`.
- **Сборка без тестов в CI** (jr:322) находкой не считается, если в том же файле есть другая команда
  Maven или Gradle, которая тесты запускает.
- Каталоги `build`, `target`, `out`, `node_modules`, `.git`, `.gradle`, `.idea` не просматриваются: там лежат копии файлов.

## Сверка кода со схемой базы данных

Правила jr:331 – jr:338, jr:391 и jr:392 собирают из миграций итоговую схему базы — таблицы, колонки, первичные ключи,
уникальные ограничения и индексы — и сверяют с ней сущности JPA и запросы. Той же схемой пользуются
правила jr:369, jr:372 и jr:373 из раздела [Гонки и целостность в базе](#гонки-и-целостность-в-базе). Такие ошибки компилятор не видит: они всплывают при запуске
приложения или при первом запросе.

| Правило | Что находит |
|---|---|
| jr:331 | поле сущности, для которого в таблице нет колонки |
| jr:332 | `@Column(nullable = false)` при колонке, допускающей `NULL`; `length`, не совпадающий с длиной колонки |
| jr:333 | метод репозитория Spring Data, в имени которого названо несуществующее свойство: `findByNmae` |
| jr:334 | запрос JPQL в `@Query`, который обращается к несуществующему полю сущности |
| jr:335 | таблица без первичного ключа |
| jr:336 | переименование таблицы или колонки и смена типа колонки: работающая версия приложения читает старое |
| jr:337 | `CREATE INDEX` на существующей таблице без `CONCURRENTLY` (PostgreSQL) |
| jr:338 | два набора изменений Liquibase с одним `id` и автором в одном файле |
| jr:391 | метод репозитория ищет по колонке, с которой не начинается ни один индекс |
| jr:392 | тип поля сущности не подходит к типу колонки: число и строка, дата и число |

Как это работает и где границы:

- **Схема строится по всем миграциям по порядку.** SQL-файлы и журналы Liquibase применяются в порядке имен
  (`V2__x.sql` раньше `V10__y.sql`): `create table`, `alter table ... add / drop / rename / alter column`,
  `drop table`, добавление ключей. Команда, которую разобрать не удалось, пропускается.
- **Без миграций сверка не идет.** Если в проекте нет ни одной миграции либо таблицы сущности в них нет,
  находок jr:331 и jr:332 не будет: схему может создавать Hibernate или другой проект.
- **Имена сверяются без учета регистра и подчеркиваний:** `createdAt`, `created_at` и `CREATED_AT` — одна
  колонка. Так сверка не зависит от стратегии именования Hibernate. Имя берется из `@Table`, `@Column`,
  `@JoinColumn`; без них — из имени класса и поля, для связи `@ManyToOne` — с окончанием `_id`.
- **Что не сверяется:** сущности с `@Inheritance`, `@SecondaryTable`, `@Subselect`, наследники других
  сущностей без своей таблицы, сущности с аннотациями на геттерах; поля `@Transient`, `@Embedded`,
  коллекции и обратные стороны связей; имена, заданные константой, а не строкой.
- **Свойства в именах методов и в JPQL** ищутся в полях сущности и ее предков из проекта. Вложенные пути
  понимаются: `findByAddressCity` и `o.customer.address.city`. Если предок или тип поля лежит вне проекта,
  свойство считается существующим — судить о нем нельзя. `id` и `class` допустимы всегда. Запросы с
  `nativeQuery = true` не проверяются.
- **Таблица-связка** из одних внешних ключей первичного ключа не требует (jr:335).
- **Переименование в той же миграции, где объект создан,** находкой не считается: его еще никто не читает.
  Миграция — это SQL-файл, набор изменений журнала Liquibase либо блок `--changeset` в SQL-файле формата
  Liquibase. Смена типа колонки получает уверенность «подозрение»: расширение типа безопасно, сужение — нет,
  а по одной команде их не различить.
- **Запрос без индекса (jr:391).** Запрос берется из имени метода Spring Data: `findByPhone`,
  `existsByEmail`, `findByCreatedAtBetween`. Индексы — из миграций: `create index`, уникальные ограничения,
  первичный ключ, `index` / `key` в `create table`; удаленный индекс не считается. Индекс помогает, когда
  начинается с одной из колонок условия: колонка, стоящая в составном индексе второй, сама по себе
  не ищется. Правило не оценивает запросы из `@Query`, условия через `Or`, поиск по части строки
  (`Containing`, `Like`) и без учета регистра, поиск по ключу, по логическому полю и по свойству,
  которого нет среди полей сущности (вложенное, унаследованное). Находка — «подозрение»: отсутствие
  индекса видно точно, но мешает оно только на большой таблице, а ее размер по коду не узнать.
- **Тип поля и тип колонки (jr:392).** Сверяются семейства: строка, число, логическое значение, дата
  и время, двоичные данные, UUID, имя константы перечисления. Длина и точность здесь ни при чем.
  Допустимо: логическое значение в числовой колонке и в колонке из одного символа, UUID в строке или
  в двоичном виде. Правило молчит для связей (`@ManyToOne`), полей с `@Convert`, `@Type`,
  `@JdbcTypeCode`, `@Lob`, `columnDefinition`, для типов с `@Converter(autoApply = true)` и для типов
  базы, о которых судить нельзя: `json`, массивы, свои типы. Перечисление, хранимое номером, показывает
  jr:84 — здесь только хранимое именем в числовой колонке.
- **Индекс без `CONCURRENTLY`** проверяется только в SQL-файлах. Если по настройкам видно, что база не
  PostgreSQL, правило молчит; если база неизвестна — находка получает уверенность «подозрение».

## Проверки тестов

Правила jr:344 – jr:348 ищут ошибки в самих тестах. Они работают, только когда каталоги `test`
сканируются (`zond.scan.skip-tests=false`). Остальные правила в тестах по умолчанию молчат —
см. [Тесты и код приложения](#тесты-и-код-приложения).

| Правило | Что находит |
|---|---|
| jr:344 | `assertEquals(actual, expected)`: ожидаемое значение стоит на месте проверяемого |
| jr:345 | проверки стоят только в `catch`, а `fail()` в `try` нет: без исключения тест проходит |
| jr:346 | результат вызова получен, но проверяются только обращения к мокам (`verify`) |

## Общие объекты с изменяемым состоянием

Бин Spring по умолчанию один на все приложение (singleton), и им одновременно пользуются все потоки.
Правила jr:360 и jr:361 ищут объекты, для которых это опасно.

| Правило | Что находит |
|---|---|
| jr:360 | объект с изменяемым состоянием объявлен бином без `@Scope("prototype")` либо создан в поле бина-одиночки |
| jr:361 | общий объект перенастраивают во время работы, либо один из потребителей настраивает бин, внедренный и в другие классы |

**Что считается объектом с состоянием (jr:360).** Не любой изменяемый класс, а те, что не рассчитаны на
несколько потоков или хранят данные одного использования:

- форматы и календарь: `SimpleDateFormat`, `DecimalFormat`, `NumberFormat`, `MessageFormat`, `Calendar`;
- криптография: `MessageDigest`, `Cipher`, `Mac`, `Signature`;
- XML: `DocumentBuilder`, `SAXParser`, `Transformer`, `XPath`, `Marshaller`, `Unmarshaller`;
- изменяемые заготовки: `WebClient.Builder`, `RestClient.Builder`, `Jackson2ObjectMapperBuilder`,
  `SimpleMailMessage`, `MimeMessageHelper`;
- соединения: `java.sql.Connection`, `Statement`, `KafkaConsumer`, `Jedis`, `EntityManager`, созданный
  вручную через `createEntityManager()`;
- в полях бинов еще `StringBuilder` и `StopWatch`.

**`RestTemplate` и `ObjectMapper` в этот список не входят намеренно.** Они потокобезопасны, пока их не
перенастраивают, и одиночкой им быть положено: создавать их на каждый вызов дорого (это ловит jr:240).
Опасна перенастройка — ее и ищет jr:361:

- **во время работы:** `objectMapper.configure(...)`, `restTemplate.getInterceptors().add(...)`,
  `jdbcTemplate.setFetchSize(...)`, `transactionTemplate.setPropagationBehavior(...)`,
  `rabbitTemplate.setExchange(...)` в обычном методе. Изменение достается всем потокам, а в список
  перехватчиков при каждом вызове добавляется еще один элемент;
- **при запуске, но чужого бина:** класс настраивает в конструкторе или `@PostConstruct` бин, который
  внедрен еще и в другие классы, — настройка меняет его поведение и для них.

Что правила советуют и чего не трогают:

- Объекту с состоянием — `@Scope("prototype")`: каждая точка внедрения получает свой экземпляр. Если новый
  экземпляр нужен на каждый вызов, его берут через `ObjectProvider<T>` или метод с `@Lookup`, а не через
  `ApplicationContext.getBean()`: так зависимость остается видна контейнеру (ручной поиск ловит jr:164).
- Для перенастройки — отдельный экземпляр: `objectMapper.copy()`, свой `RestTemplate` через
  `RestTemplateBuilder`, бин с `@Qualifier` либо тот же prototype.
- Не считаются находкой: настройка своего объекта (`new RestTemplate()` в поле) при запуске; настройка в
  классах `@Configuration` и реализациях `...Configurer` / `...Customizer`; бин с `@Qualifier`; бин,
  объявленный с областью prototype; копия и локальная переменная; поле, к которому обращаются только под
  `synchronized`.
- Проверяются типы по именам из списка; одноименный класс самого проекта пропускается, а `Connection`,
  `Statement` и `ResultSet` учитываются только при импорте из `java.sql`.

### Устаревшие синхронизированные коллекции

| Правило | Что находит | Уровень |
|---|---|---|
| jr:426 | `new Hashtable`, `new Vector`, `new Stack` и обертка `Collections.synchronized...` в общем поле | MINOR |

У `Hashtable`, `Vector` и `Stack` каждый метод `synchronized`: блокировка берется на каждый вызов, даже если
коллекцию видит один поток, а составные действия (проверить и добавить, обойти) атомарными все равно не
становятся. `Hashtable` к тому же не принимает null - `put(key, null)` бросит `NullPointerException`. Обертка
`Collections.synchronizedList/Map/Set(...)` дает то же самое: одна блокировка на всю коллекцию, а обход и
составные действия приходится отдельно заключать в `synchronized (list)` - об обходе без него говорит
jr:245.

```java
// jr:426: каждый вызов ждет общую блокировку, а if (!contains) add - все равно гонка
private final List<Session> sessions = Collections.synchronizedList(new ArrayList<>());
private final Map<String, Client> clients = new Hashtable<>();

// коллекции java.util.concurrent делают составные действия сами
private final List<Session> sessions = new CopyOnWriteArrayList<>();
private final Map<String, Client> clients = new ConcurrentHashMap<>();
clients.computeIfAbsent(id, this::connect);
```

- **Замена.** `Hashtable` - `HashMap`, а для нескольких потоков `ConcurrentHashMap`; `Vector` - `ArrayList`
  либо `CopyOnWriteArrayList`; `Stack` - `ArrayDeque` (у `Stack` к тому же обход идет снизу вверх, а не в
  порядке `pop()`). Для обертки совет зависит от того, что обернуто: `ArrayList` - `CopyOnWriteArrayList`
  или `ConcurrentLinkedQueue`, `LinkedList` - `ConcurrentLinkedDeque`, `HashMap` - `ConcurrentHashMap`,
  `HashSet` - `ConcurrentHashMap.newKeySet()`, `TreeMap` и `TreeSet` - `ConcurrentSkipListMap` и
  `ConcurrentSkipListSet`.
- **Обертка считается только в общем поле:** статическом поле любого класса либо поле singleton-бина -
  в том числе присвоенном в конструкторе. В локальной переменной и в поле обычного объекта она лишняя, а
  не опасная.
- **Не считаются.** Обертки над `LinkedHashMap` (порядок, LRU на `removeEldestEntry`), `WeakHashMap`,
  `IdentityHashMap` и анонимными классами: конкурентной замены в JDK у них нет, и обертка - честный выбор.
  `Hashtable` и `Vector` для старых API, которые сами их требуют: окружение JNDI (`new InitialDirContext(env)`,
  `env.put(Context.PROVIDER_URL, ...)`) и модели Swing (`DefaultTableModel`, `JComboBox`, `JList`). `Properties`
  (наследник `Hashtable`) не считается. Тесты не проверяются.

## Поиск перебором вместо Map

Правило jr:362 ищет места, где элемент коллекции находят по ключу перебором, хотя `Map` дала бы доступ
сразу.

- **Поиск на каждой итерации цикла** — стрим с `filter` / `anyMatch` по равенству свойства либо вложенный
  цикл с таким же `if`. Вместе с внешним циклом это O(N×M); совет — собрать `Map` перед циклом
  (`Collectors.toMap`, для нескольких значений — `groupingBy`).
- **Метод поиска по ключу** — `findById(id)`, который перебирает поле-коллекцию. Насколько это медленно,
  зависит от размера коллекции и частоты вызовов, поэтому находка получает уверенность «подозрение».
- Не считаются находкой: поиск постоянного значения; поиск в коллекции самого элемента
  (`order.getLines()`); коллекция, перечисленная в коде (`List.of(...)`); внешний цикл по значениям
  перечисления; произвольное условие вроде `handler.supports(request)`; тесты.
- Поиск по ключу в цикле раньше показывало jr:75 (стрим в цикле) с общим советом; теперь такие случаи
  показывает только jr:362, а jr:75 оставляет себе остальные стримы. Поиск элемента целиком
  (`list.contains(x)`) по-прежнему ловит jr:71 — там нужен `Set`.

## Очереди сообщений

Правила jr:363 – jr:368 проверяют работу с RabbitMQ и Kafka: слушателей (`@RabbitListener`,
`@KafkaListener`, `@JmsListener`, `@SqsListener`) и отправку через `RabbitTemplate`, `KafkaTemplate`,
`JmsTemplate`, `StreamBridge`.

| Правило | Что находит |
|---|---|
| jr:363 | слушатель ловит `Exception` / `RuntimeException` / `Throwable` и только пишет в лог — сообщение потеряно |
| jr:364 | слушатель бросает исключение, а в проекте нет ни очереди ошибок, ни ограничения повторов |
| jr:365 | сообщение отправляется внутри `@Transactional`-метода, до коммита |
| jr:366 | результат `kafkaTemplate.send(...)` никто не проверяет |
| jr:367 | ручное подтверждение: до обработки, не на всех ветках либо ни разу |
| jr:368 | слушатель создает запись в БД без защиты от повторной доставки |
| jr:396 | режим подтверждения `NONE` у слушателя RabbitMQ: сообщение удаляется из очереди до обработки |

- **jr:363** смотрит только на `try`, который охватывает работу слушателя целиком. Сохранение сбойного
  сообщения, отправка в другую очередь, проброс исключения — обработка, а не потеря. Конкретное исключение
  (`JsonProcessingException`) ловят намеренно. `try` вокруг одного элемента пачки и слушатель с ручным
  подтверждением — случаи других правил.
- **jr:364** — одна находка на брокера, у первого слушателя; в сообщении сказано, сколько их всего.
  Для RabbitMQ защитой считаются `default-requeue-rejected=false`, `retry.enabled=true`,
  `x-dead-letter-exchange`, `AmqpRejectAndDontRequeueException`, свой обработчик ошибок, `basicNack`;
  для Kafka — `DeadLetterPublishingRecoverer`, `@RetryableTopic`, `DefaultErrorHandler`. Правило не
  разбирает, как именно это настроено: достаточно, что настроено. Слушатель, который сам глушит все
  исключения, в счет не идет — им занимается jr:363.
- **jr:365** ищет отправку и в самом методе, и в методах, которые он вызывает (`max-call-depth`).
  Не считаются: транзакция `readOnly`, отправка из `afterCommit()` и из `@Async`-метода, проект
  с транзакционным отправителем (`spring.kafka.producer.transaction-id-prefix`, `KafkaTransactionManager`,
  `setChannelTransacted`).
- **jr:366** молчит, если результат используется (`whenComplete`, `get`, `return`), если в проекте есть
  свой `ProducerListener` и внутри `executeInTransaction`.
- **jr:367** относится к слушателям с параметром `Acknowledgment` (Kafka) или `Channel` (RabbitMQ).
  Для `Channel` находка «ни разу не подтверждает» выдается только при `ackMode = "MANUAL"`: без ручного
  режима канал нужен для другого. Объект, переданный в другой метод, считается подтвержденным там.
- **jr:368** — подозрение: защита может стоять в базе. Вставкой считается сохранение объекта, созданного
  в этом же коде (`new`, билдер, преобразователь), и `insert` через `JdbcTemplate`. Защитой — поиск в том же
  репозитории перед сохранением, перехват `DataIntegrityViolationException`, `on conflict` / `merge`
  в запросе, имена со словами `idempot`, `dedup`, `duplicate`.

- **jr:396** смотрит и настройки (`spring.rabbitmq.listener.simple.acknowledge-mode=none`, то же для
  `direct`), и код: `setAcknowledgeMode(AcknowledgeMode.NONE)`, `@RabbitListener(ackMode = "NONE")`.
  Настройки тестов и профилей разработки не считаются. Находка «подтверждена».

## Гонки и целостность в базе

Правила jr:369 – jr:373 и jr:390 ищут то, что ломается под нагрузкой или на «неудобных» данных. Три из них сверяют
код со [схемой из миграций](#сверка-кода-со-схемой-базы-данных).

| Правило | Что находит |
|---|---|
| jr:369 | «проверил — вставил»: `existsBy…` / `findBy…`, затем `save`, а уникального ограничения нет |
| jr:370 | «прочитал — изменил — записал»: `x.setTotal(x.getTotal() + n)` без блокировки и без `@Version` |
| jr:371 | исключение из другого транзакционного метода поймано в `@Transactional`-методе без проброса |
| jr:372 | имя константы перечисления при `@Enumerated(STRING)` длиннее колонки |
| jr:373 | `@Size(max)` / `@Length(max)` допускает строку длиннее, чем вмещает колонка |
| jr:390 | блокировка берется и отпускается внутри `@Transactional`-метода — раньше, чем транзакция закоммитится |

- **jr:369.** Колонки берутся из имени метода: `findByEmailAndTenantId` → `email`, `tenant_id`. Условия
  сложнее равенства (`Containing`, `Between`, `Or`) не рассматриваются. Уникальность ищется в схеме
  (ограничение, уникальный индекс, первичный ключ — в том числе составные и добавленные или удаленные
  позже), в `@Column(unique = true)` и в `@Table(uniqueConstraints = ...)`. Есть миграции и ограничения
  в них нет — находка «вероятно»; миграций для таблицы нет — «подозрение». После `findBy…` вставкой
  считается только сохранение объекта, созданного здесь же: найденную запись могли просто обновить.
  Правило молчит, если метод работает под блокировкой (`lock()`, `tryLock()`, `synchronized`), если
  транзакция `SERIALIZABLE` и если ошибку дубликата ловят (`DataIntegrityViolationException`).
  Блокировку, которая стоит внутри транзакции и потому не защищает, показывает jr:390.
- **jr:370.** Сущность должна быть прочитана из репозитория в этом же методе: параметр и поле приходят
  неизвестно откуда. Не считаются: сущность с `@Version` (в том числе в предке; предок вне проекта тоже
  считается версионированным), чтение методом с `@Lock` или с `ForUpdate` / `Lock` в имени, метод
  с `LockModeType`, `synchronized`. Приклеивание строки к строке счетчиком не считается.
- **jr:371.** Вызванный метод должен принадлежать другому бину и участвовать в той же транзакции: метод
  с `REQUIRES_NEW`, `NESTED`, `noRollbackFor` и метод своего же класса (вызов мимо прокси) транзакцию
  к откату не помечают. Из вызовов репозитория учитываются те, что обращаются к базе сразу:
  `saveAndFlush`, `flush`, `deleteById`. Ловить должны непроверяемое исключение; `catch (IOException)`
  не считается.
- **jr:390.** Транзакцию коммитит прокси уже после выхода из метода, то есть после `unlock`: следующий
  поток получает блокировку и читает из базы данные до изменения. Находкой считаются три случая: метод
  одновременно `synchronized` и `@Transactional`; блок `synchronized` с обращением к базе внутри
  транзакционного метода; пара `lock()` / `tryLock()` и `unlock()` на одном объекте — `Lock`, Redisson,
  своя распределенная блокировка. Не считаются: блокировка в методе без транзакции, который вызывает
  транзакционный (так и надо); транзакция `readOnly`, `NOT_SUPPORTED` и `NEVER`; `unlock` из
  `afterCommit()` / `afterCompletion()`; блокировка строки в базе (`entityManager.lock`, `@Lock`);
  блок `synchronized` вокруг карты в памяти; закрытые методы — на них `@Transactional` не действует.
- **jr:372 и jr:373.** Длина берется из миграций — тогда находка «подтверждена»; если колонки в миграциях
  нет или тип без длины (`text`), то из `@Column(length = ...)` — тогда «вероятно». Без того и другого
  правило молчит. Перечисление ищется по имени среди классов проекта.

## Подбор уникального кода

Короткий код приглашения, PIN, номер заказа из шести цифр часто подбирают так: сгенерировать случайное
значение, проверить, что такого еще нет, и повторить. Коротких кодов конечное число. Когда они почти
закончились, цикл без предела попыток крутится очень долго, а когда закончились совсем - бесконечно, и
каждая попытка - еще один запрос в базу. Цикл с пределом, который после последней попытки возвращает
`null` или последний, уже занятый код, прячет ту же ошибку до вставки дубликата.

| Правило | Что находит | Уровень |
|---|---|---|
| jr:425 | подбор уникального случайного кода в цикле без предела попыток либо без исключения после последней попытки | MAJOR |

```java
// jr:425: когда шестизначные коды закончатся, цикл не закончится никогда
while (true) {
    String code = RandomStringUtils.randomNumeric(6);
    if (!inviteRepository.existsByCode(code)) {
        return code;
    }
}

// так попыток не больше заданного, а их исчерпание - явная ошибка
for (int i = 0; i < attempts; i++) {
    String code = RandomStringUtils.randomNumeric(length);
    if (inviteRepository.findByCode(code).isEmpty()) {
        return code;
    }
}
throw new IllegalStateException("Не удалось подобрать уникальный код за " + attempts + " попыток");
```

- **Что считается подбором.** Цикл (`while`, `do-while`, `for`), в котором переменная получает случайное
  значение - `RandomStringUtils.randomNumeric(...)`, `random.nextInt(...)`, `StringUtils.randomAlphanumeric(...)`,
  обрезок UUID (`randomUUID().toString().substring(0, 8)`, `hashCode()`), строка, собранная по символам
  через `append` - в том числе через другие переменные (`name = base + "-" + suffix`), и эта переменная
  уходит в проверку уникальности: `exists...`, `find...By...`, `count...By...`, `contains`, `containsKey`,
  `isUnique...`, `isTaken...`. Цикл заканчивается, когда код нашелся: `return`, `break` либо проверка в
  условии `do { ... } while (repository.existsByCode(code))`.
- **Две находки.** «Без предела попыток» - в условии цикла нет сравнения со счетчиком, и внутри нет
  `if (++attempts > MAX) throw / break`. «Без исключения после последней попытки» - предел есть, но сразу
  за циклом нет ни `throw`, ни проверки `if (code == null) throw ...`, а внутри цикла исчерпание не
  бросает исключение.
- **Уверенность.** Если длина кода видна в коде, правило считает число вариантов: `randomNumeric(6)` -
  миллион, `nextInt(10000)` - десять тысяч, и находка «вероятно». От миллиарда вариантов коды на практике не
  кончаются (`randomAlphanumeric(6)` - 56 миллиардов), находка остается, но как «подозрение». Длина из
  настроек неизвестна - «вероятно».
- **Не считаются.** Полный `UUID.randomUUID()` - его не исчерпать; пакетная генерация (`for` по числу
  нужных кодов без выхода при удаче); случайная пауза в цикле ожидания; тесты.

## Кеш и память

| Правило | Что находит |
|---|---|
| jr:374 | карта в бине-одиночке или статическом поле, в которую записи только добавляют |
| jr:375 | кеш `@Cacheable`, который нигде не сбрасывается и не имеет срока жизни |
| jr:376 | `@CacheEvict` / `@CachePut` внутри транзакции, до ее коммита |
| jr:377 | объект, полученный из `@Cacheable`-метода, меняют на месте |

- **jr:374.** Карта должна быть создана обычным конструктором (`HashMap`, `ConcurrentHashMap`, ...)
  в закрытом поле. Не считаются: карта, из которой удаляют (`remove`, `clear`, `removeIf` — в том числе
  через `entrySet()`), которую заменяют новой, возвращают или передают наружу; ключ-перечисление,
  `Class`, `Boolean`; постоянный ключ (`"default"`, `Kind.FAST`); наполнение при запуске и в методах
  вроде `register...` / `init...` / `load...` / `read...`; `WeakHashMap` и `LinkedHashMap` с `removeEldestEntry`.
- **jr:375.** Сбросом считаются `@CacheEvict`, `@CachePut` (в том числе в `@Caching`) и
  `cacheManager.getCache("имя")`. Если в проекте задан срок жизни (`expireAfterWrite`, `entryTtl`,
  `spring.cache.redis.time-to-live`, `expire` в `spring.cache.caffeine.spec`) либо кеш настроен внешним
  файлом (`spring.cache.jcache.config`), правило молчит целиком. Имя, заданное константой, берется как
  есть: `CacheNames.USERS` → `USERS`.
- **jr:376.** Два случая: `@CacheEvict` и `@Transactional` на одном методе; метод с `@CacheEvict` вызван
  из транзакционного метода другого бина. Транзакция `readOnly` не считается. Правило молчит, если
  менеджер кеша транзакционный: `TransactionAwareCacheManagerProxy`, `transactionAware()`.
- **jr:377.** Изменением считаются `add`, `remove`, `clear`, `sort`, `put`, сеттеры и
  `Collections.sort(...)` на переменной с результатом либо прямо в цепочке. Копия
  (`new ArrayList<>(cached())`) и переменная, которой позже присвоили другое значение, не считаются.
  Для кеша вне памяти приложения (`spring.cache.type=redis`, `RedisCacheManager`) правило молчит: там
  каждый раз приходит новый объект.

## Файлы в памяти

Собрать файл в `byte[]` и вернуть его - самый короткий путь, и на маленьких файлах он работает.
Но память на запрос при этом растет вместе с размером файла и умножается на число одновременных
запросов: сервис, который уверенно отдает выгрузку на тысячу строк, падает с `OutOfMemoryError` на
выгрузке в миллион. Правила jr:401 – jr:409 находят места, где файл целиком оказывается в памяти:
когда его собирают, читают, отдают или хранят.

| Правило | Что находит |
|---|---|
| jr:401 | файл собирается в `ByteArrayOutputStream`: запись в цикле по данным либо документ, записанный в буфер |
| jr:402 | текстовый файл копится в `StringBuilder` или склеивается в одну строку, а затем превращается в `byte[]` |
| jr:403 | файл отдается в HTTP-ответе массивом байт, а не потоком |
| jr:404 | файл целиком уходит телом сообщения в очередь |
| jr:405 | файл или поток читается в память целиком |
| jr:406 | ответ другого сервиса или объект из хранилища читается в `byte[]` |
| jr:407 | содержимое файла лежит в поле сущности (`@Lob`, `byte[]`) |
| jr:408 | файлы копятся в поле бина, в статическом поле или в кеше |
| jr:409 | `File.deleteOnExit()` в сервисе |

```java
// jr:401: буфер растет вместе с выборкой, toByteArray() делает еще одну копию
try (ByteArrayOutputStream out = new ByteArrayOutputStream();
     CSVPrinter printer = new CSVPrinter(new PrintWriter(out), format)) {
    for (Row row : rows) {
        printer.printRecord(row.values());
    }
    return out.toByteArray();
}

// так память на файл - только буфер записи
void write(List<Row> rows, OutputStream out) throws IOException {
    CSVPrinter printer = new CSVPrinter(new OutputStreamWriter(out, StandardCharsets.UTF_8), format);
    for (Row row : rows) {
        printer.printRecord(row.values());
    }
    printer.flush();
}

// в контроллере
StreamingResponseBody body = out -> generator.write(rows, out);
```

- **jr:401.** Буфером считаются `ByteArrayOutputStream` и его аналоги из Spring и Commons IO вместе с
  обертками над ними: `PrintWriter`, `CSVPrinter`, `ZipOutputStream` и любой объект, созданный от буфера.
  Находка есть в трех случаях: запись в буфер или обертку идет в цикле по данным; в буфер целиком
  записывается документ (`workbook.write(out)`, `document.save(out)`); буфер передан методу, название
  которого говорит о выгрузке (`csvExporter.write(rows, out)`) - у последнего уверенность «подозрение»,
  потому что сколько он пишет, по вызову не видно. Не считаются: запись по одному байту и цикл по байтам
  или символам одного значения (кодирование, сборка кадра), цикл повторных попыток, буфер, который
  создается заново на каждой итерации, копирование потока (о нем говорит jr:405) и код, работающий
  при запуске приложения. Находка ставится на объявление буфера.
- **jr:402.** `builder.toString().getBytes()`, где в `StringBuilder`, `StringBuffer`, `StringWriter` или
  `StringJoiner` дописывают в цикле по данным; строка может пройти через переменную. Склейка
  `String.join(...)` и `Collectors.joining(...)` считается, только когда разделитель - перевод строки:
  `"\n"`, `System.lineSeparator()`, константа с именем вроде `LINE_SEPARATOR`; уверенность у нее
  «подозрение». Строка, которую не превращают в байты, и шестнадцатеричная запись значения находкой
  не являются.
- **jr:403.** Три вида мест: `ResponseEntity...body(x)`, где `x` - `byte[]`, `ByteArrayResource` или
  `InputStreamResource` поверх `ByteArrayInputStream`; `response.getOutputStream().write(bytes)`;
  обработчик, который возвращает `byte[]`, `ResponseEntity<byte[]>` или `ByteArrayResource`. Что в ответе
  именно файл, правило узнает по методу: `Content-Disposition`, `attachment`, тип `octet-stream`, PDF,
  Excel, CSV, ZIP, а для обработчика - еще и по его имени и адресу (`download`, `export`, `report`).
  Если заголовки задаются в другом месте, а о файле говорит только название данных (`body(report)`),
  уверенность - «подозрение». Картинка с кодом (`image/png` без признаков файла) и тело исходящего
  запроса (`restClient.post().body(payload)`) не считаются.
- **jr:404.** `MessageBuilder.withBody(x)` / `withPayload(x)`, `new Message(x, ...)`,
  `new ProducerRecord<>(topic, x)` и отправка через `RabbitTemplate`, `KafkaTemplate`, `JmsTemplate`.
  Файлом считается `byte[]`, который так назван (`file`, `report`, `attachment`, `xlsx`...) либо получен
  из `buffer.toByteArray()`, `readAllBytes()` или `MultipartFile.getBytes()`. Объект, превращенный в байты
  (`writeValueAsBytes`, `json.getBytes()`, `toByteArray()` у protobuf), - обычное сообщение.
- **jr:405.** `Files.readAllBytes` / `readAllLines` / `readString`, `InputStream.readAllBytes()`,
  `IOUtils.toByteArray` / `toString`, `StreamUtils.copyToByteArray`, `FileCopyUtils`, `FileUtils`,
  `ByteStreams.toByteArray`, `resource.getContentAsByteArray()`, а также копирование потока в
  `ByteArrayOutputStream`: `in.transferTo(buffer)`, `IOUtils.copy(in, buffer)` и цикл с `read` и `write`
  (одна находка на цикл). Правило молчит, когда размер известен заранее: ресурс из сборки
  (`getResourceAsStream`, `ClassPathResource`), ключ, сертификат, шаблон, настройки, скрипт - по
  названиям в вызове, в методе и в классе; при чтении во время запуска; для текста ответа другого сервиса
  (`IOUtils.toString(response.body()...)`) и для буфера `ContentCachingResponseWrapper`. Уверенность
  «вероятно» - если данные названы файлом либо метод принимает `MultipartFile`, `InputStream`, `File`
  или `Path`; иначе «подозрение». В проекте без контроллеров, слушателей очередей и задач по расписанию
  (утилита командной строки, библиотека) все находки - «подозрение»: там файлы читают по одному.
- **jr:406.** `byte[].class` типом ответа у `RestTemplate`, `RestClient` и `WebClient`,
  `HttpResponse.BodyHandlers.ofByteArray()`, `response.body().bytes()` у OkHttp, `getObjectAsBytes` и
  `ResponseTransformer.toBytes()` у AWS SDK, метод `@FeignClient` или `@HttpExchange`, возвращающий
  `byte[]` либо `ResponseEntity<byte[]>`. Небольшие ответы - QR-код, капча, значок, аватар - по названиям
  в вызове, методе и классе не считаются.
- **jr:407.** `@Lob byte[]` в сущности - «вероятно»; `byte[]` без `@Lob` и `@Lob String` - «подозрение» и
  только если поле названо как содержимое файла (`content`, `attachment`, `photo`, `document`, `data`).
  Не считаются: поле с `@Basic(fetch = FetchType.LAZY)`, колонка длиной до 4096, хеш, соль, подпись,
  ключ и другие короткие двоичные значения, `@Lob String` с обычным длинным текстом, `Blob` и `Clob` -
  они читаются потоком.
- **jr:408.** Поле бина или статическое поле типа `Map`, `List`, `Cache`, `Queue` и подобных со
  значениями `byte[]`, `ByteArrayOutputStream`, `ByteArrayResource`, `MultipartFile`, `ByteBuffer`, в
  которое добавляют во время работы (`put`, `add`, `offer`, `computeIfAbsent`...). Набор постоянных
  значений (`Map.of(...)`) и поле, заполненное один раз при запуске, не считаются; поле обычного
  объекта - тоже: оно живет, пока жив объект. Отдельный случай - метод с `@Cacheable` или `@CachePut`,
  который возвращает `byte[]` или `ByteArrayResource`.
- **jr:409.** Не считаются вызов в методе `main` и при запуске приложения: один файл на весь срок
  работы утечкой не является.

Чего правила не видят: данные, из которых собирается файл, тоже могут целиком лежать в памяти
(список на миллион строк, таблица «строки × колонки»), а пределы запроса - ограничивать строки и колонки
по отдельности, но не их произведение. Это свойство алгоритма, а не отдельной строки кода; о выборке
без страниц сообщают jr:86 и jr:385.

## Рекурсивный разбор документов

Обойти дерево XML или JSON рекурсией - самый короткий способ: метод разбирает узел и вызывает сам себя для
каждого вложенного. Но каждый уровень вложенности - еще один вызов в стеке потока, а глубину задает сам
файл. На глубоко вложенном документе (в том числе собранном специально) поток падает со
`StackOverflowError`. Это `Error`: обычный `catch (Exception)` его не поймает, и запрос обрывается целиком.
Если элементы класть в отдельную очередь и разбирать их в цикле, необработанные узлы лежат в куче, и
глубину ограничивает только память.

| Правило | Что находит | Уровень |
|---|---|---|
| jr:424 | рекурсивный обход и разбор документа XML, JSON или YAML | MAJOR |

```java
// jr:424: глубина стека равна глубине вложенности документа
void collect(Node node, List<String> values) {
    if (node.getNodeType() == Node.TEXT_NODE) {
        values.add(node.getTextContent());
    }
    NodeList children = node.getChildNodes();
    for (int i = 0; i < children.getLength(); i++) {
        collect(children.item(i), values);
    }
}

// так узлы ждут своей очереди в куче, а стек не растет
void collect(Node root, List<String> values) {
    Deque<Node> pending = new ArrayDeque<>();
    pending.push(root);
    while (!pending.isEmpty()) {
        Node node = pending.pop();
        if (node.getNodeType() == Node.TEXT_NODE) {
            values.add(node.getTextContent());
        }
        NodeList children = node.getChildNodes();
        for (int i = children.getLength() - 1; i >= 0; i--) {
            pending.push(children.item(i));
        }
    }
}
```

- **Что считается документом.** Узлы дерева: `JsonNode`, `ObjectNode`, `ArrayNode` (Jackson),
  `JsonElement`, `JsonObject`, `JsonArray` (Gson, Vert.x, `javax.json`), `JSONObject`, `JSONArray`
  (org.json, fastjson), `NodeList`. `Node`, `Element` и `Document` есть во многих библиотеках, поэтому
  они считаются, только если импортированы из пакетов дерева XML или YAML: `org.w3c.dom`, dom4j, JDOM,
  XOM, SnakeYAML. Узел дерева разбора Java (`com.github.javaparser.ast.Node`) не документ: его глубину
  задает исходный код. Отдельно - потоковые читатели `JsonParser`, `JsonReader`, `XMLStreamReader`,
  `XMLEventReader`: рекурсивный разбор передает в себя тот же читатель и спускается на уровень ниже.
- **Что считается рекурсией.** Метод вызывает сам себя - в том числе из лямбды
  (`node.fields().forEachRemaining(field -> flatten(..., field.getValue()))`) и ссылкой на метод
  (`array.forEach(this::update)`) - и передает в вызов узел, до которого дошел от своего параметра:
  `children.item(i)`, `node.get(key)`, переменную цикла по узлу, параметр лямбды в `node.forEach(...)`,
  результат `instanceof JSONObject nested`. Взаимная рекурсия внутри класса - `readValue -> readObject ->
  readValue` - тоже считается; о цикле сообщается один раз, на первом его методе, и в тексте находки
  виден весь цикл.
- **Когда находки нет.** Метод сам ограничивает глубину: принимает `depth`, `level` или `nesting` и
  сравнивает его с пределом (`if (depth > MAX_DEPTH) throw ...`). Счетчик `indent` пределом не является -
  он отступ, а не проверка. Не спуск по документу: тот же узел дальше (`print(node, path + "/")`), новый
  объект (`validate(new DOMSource(node))` - это другая перегрузка), результат другой функции
  (`merge(parent, translation)` при обходе иерархии клиентов) и обход полей класса через рефлексию
  (`walkInto(Class<?> type, JsonNode json)`). Тесты не проверяются.
- **Пределы парсеров.** У некоторых парсеров есть свой предел вложенности - у Jackson с версии 2.15 это
  1000 уровней по умолчанию (`StreamReadConstraints`), - но его поднимают настройкой, а парсеры DOM и StAX
  из JDK при обычных настройках глубину не ограничивают (`jdk.xml.maxElementDepth=0`). Рекурсия, у которой каждый уровень держит в стеке несколько
  переменных, может закончиться и раньше предела парсера, поэтому правило не делает исключений по
  библиотеке.

## Квадратичные алгоритмы на коллекциях

Код, который на сотне элементов работает мгновенно, а на ста тысячах - минуты: внутри цикла по данным
стоит операция, которая сама перебирает все уже обработанное. Правила jr:410 – jr:415 находят такие места
и общий на все потоки генератор случайных чисел. Рядом с ними работают jr:71 (`contains` в цикле),
jr:75 (стрим в цикле) и jr:362 (поиск перебором вместо `Map`).

| Правило | Что находит |
|---|---|
| jr:410 | проверка на повтор через `contains` перед `add`: перебор списка вместо множества и двойной поиск в множестве |
| jr:411 | неповторяющиеся элементы выбирают по случайному индексу и отбрасывают повторы |
| jr:412 | сортировка в цикле: заново после каждой вставки либо одной и той же неизменной коллекции |
| jr:413 | один генератор случайных чисел на все потоки, созданный без seed |
| jr:414 | максимум, минимум или сумма пересчитываются в цикле с нуля |
| jr:415 | `list.indexOf(x)` в цикле |

```java
// jr:410: каждое добавление перебирает все, что добавлено раньше
if (values.contains(value)) {
    continue;
}
values.add(value);

// так поиск занимает O(1), а add сам говорит, был ли элемент
if (!seen.add(value)) {
    continue;
}
values.add(value);
```

```java
// jr:414: на каждом шаге максимум ищется заново по всем элементам до текущего
for (int i = 0; i < values.size(); i++) {
    int max = Collections.max(values.subList(0, i + 1));
    process(max);
}

// так - один проход
int max = Integer.MIN_VALUE;
for (int value : values) {
    max = Math.max(max, value);
    process(max);
}
```

- **jr:410.** Пара ищется в одном методе: `коллекция.contains(x)` и следом `коллекция.add(x)` с тем же
  получателем и тем же аргументом. Для списка (`List`, `ArrayList`, `LinkedList`) находка есть, когда
  проверка стоит в цикле по данным либо список - поле (он растет от вызова к вызову; уверенность тогда
  «подозрение»). Если список потом сортируется, сообщение советует `TreeSet`. Для множества находка
  уровня MINOR и только для пары, которую можно заменить одним вызовом: проверка составляет все условие,
  а `add` идет первым в ветке `if (!set.contains(x))` либо сразу за
  `if (set.contains(x)) { return / continue / break / throw }`. Если у условия есть вторая половина
  (`!set.contains(x) && isValid(x)`) либо между проверкой и добавлением стоит другой код, одним `add`
  пару не заменить - находки нет. Разовая проверка локального списка вне цикла
  не считается. О такой паре jr:71 больше не сообщает: одна строка - одна находка.
- **jr:411.** В цикле `while`, `do` или `for` элемент берется как `source.get(random.nextInt(source.size()))`,
  `source[(int) (Math.random() * source.length)]` либо по переменной с таким индексом, и там же
  выбранное проверяется на повтор: `contains`, `containsKey` или `add`, по результату которого что-то
  решают, - по элементу или по индексу. Выбор с повторами и `Collections.shuffle` не считаются.
  На один цикл - одна находка.
- **jr:412.** `Collections.sort(x)`, `Arrays.sort(x)` и `x.sort(...)` в цикле, если `x` объявлен до
  цикла. Сообщений два: список пополняется в этом же цикле (`add`, `addAll`, `offer`) - его сортируют
  заново после каждой вставки, нужен `TreeSet`, `TreeMap`, `PriorityQueue` либо одна сортировка после
  цикла; список в цикле не меняется - сортировку нужно вынести перед циклом. Свой список у каждой
  итерации (`group.items().sort(...)`) и цикл повторных попыток не считаются. Разовая сортировка находкой
  не является: `Collections.sort` на готовом списке быстрее сборки дерева, а `TreeSet` к тому же
  выбросил бы одинаковые элементы.
- **jr:413.** Поле типа `Random` или `SecureRandom`, статическое либо в бине-одиночке, созданное без
  аргументов и без `setSeed`. Находка есть, когда из генератора берут значения в цикле либо отдают его
  другому коду (аргументом, присваиванием, из метода): одно число на вызов узким местом не бывает.
  Правило молчит, если по названию поля, класса или методов видно, что генератор делает секреты
  (`token`, `password`, `salt`, `nonce`, `otp`, `secret`, `jwt`, `csrf`...): им положен `SecureRandom`,
  и о них говорит jr:137. Уверенность «вероятно» - для `Random` в проекте, где есть обработчики
  запросов, `@Async`, исполнители, `CompletableFuture` или параллельные стримы; для `SecureRandom` и для
  проекта без потоков - «подозрение»: заменять криптостойкий генератор можно, только убедившись, что
  значения не секретны.
- **jr:414.** `Collections.max` и `Collections.min` в цикле, если коллекция объявлена до цикла, а также
  `max`, `min`, `sum`, `average`, `count`, `reduce` у стрима по срезу (`values.subList(...).stream()`).
  Сообщений три: по срезу списка; по коллекции, которая пополняется в этом же цикле, - в обоих случаях
  значение нужно вести на лету; по коллекции, которая в цикле не меняется, - вычислить один раз перед
  циклом. Своя коллекция у каждой итерации не считается. О стриме прямо по внешней коллекции
  (`values.stream().max(...)`) сообщает jr:75.
- **jr:415.** `indexOf` и `lastIndexOf` у списка, объявленного до цикла; `String.indexOf` не считается.
  Если ищется позиция элемента, который сам сейчас перебирается (`for (Item item : items) {
  items.indexOf(item) }`), сообщение советует счетчик или цикл с индексом: при одинаковых элементах
  `indexOf` еще и вернет не тот индекс. В остальных случаях - построить `Map<элемент, индекс>` одним
  проходом.

## Лишняя работа в циклах и пулы потоков

Правила jr:416 – jr:422 продолжают предыдущий раздел: это места, где код делает больше, чем нужно, -
ищет дважды, сдвигает весь список ради одного элемента, заново создает дорогой объект - либо мешает
потокам работать одновременно.

| Правило | Что находит |
|---|---|
| jr:416 | `map.containsKey(key)` и следом `get` или `put` с тем же ключом: двойной поиск |
| jr:417 | `removeAll`, `retainAll`, `containsAll`, в которых поиск идет перебором списка |
| jr:418 | `list.remove(0)` и `list.add(0, x)` в цикле: сдвиг всего списка на каждой итерации |
| jr:419 | дорогой объект создается заново на каждой итерации, хотя от нее не зависит |
| jr:420 | `UUID.randomUUID()` в цикле внутри задач, которые выполняются параллельно |
| jr:421 | список или массив сортируют ради одного элемента - первого или последнего |
| jr:422 | пул потоков большого постоянного размера, не связанного с числом ядер |

- **jr:416.** Карта должна быть объявлена как `Map`, `HashMap`, `LinkedHashMap`, `TreeMap` и подобные;
  о конкурентных картах сообщает jr:172 - там пара вызовов уже гонка. Повторное обращение ищется в том же
  операторе (ветки `if`, условие, `?:`), а если проверка стоит в `if` и внутри него обращений нет - в
  операторах после него (`if (!map.containsKey(key)) { throw ...; } value = map.get(key);`). Совет зависит
  от того, что делают дальше: значение обновляют из прежнего - `merge`; кладут, только если ключа нет, -
  `putIfAbsent` или `computeIfAbsent`; только читают - один `get` с проверкой на null либо `getOrDefault`.
  Пара вызовов оправдана, когда в карте хранят null: об этом сказано в сообщении.
- **jr:417.** `x.removeAll(list)` и `x.retainAll(list)` - когда аргумент объявлен списком;
  `list.containsAll(other)` - когда списком объявлен получатель. Список, записанный прямо в вызове
  (`List.of("a", "b")`), мал и не считается. В сообщении - готовая замена: `new HashSet<>(...)`.
- **jr:418.** `remove(0)`, `removeFirst()`, `add(0, x)`, `addFirst(x)` у списка, объявленного до цикла
  как `List`, `ArrayList`, `CopyOnWriteArrayList` или `Vector`. Список, созданный как `LinkedList`,
  `Deque` и `ArrayDeque`, удаление по значению (`remove(element)`) и свой список у каждой итерации
  не считаются.
- **jr:419.** `DateTimeFormatter.ofPattern`, `new SimpleDateFormat`, `new DecimalFormat`,
  `NumberFormat.getInstance`, `MessageDigest` / `Cipher` / `Mac` / `Signature` / `KeyFactory.getInstance`,
  `JAXBContext.newInstance`, фабрики XML (`DocumentBuilderFactory.newInstance` и другие), `new SecureRandom()`,
  HTTP-клиенты (`HttpClient.newHttpClient`, `new RestTemplate()`, `WebClient.builder()`, `new OkHttpClient()`)
  и поиск через рефлексию (`getDeclaredFields`, `getMethod`, `Class.forName`). Находка есть, только когда
  выражение не зависит от цикла: `DateTimeFormatter.ofPattern(row.pattern())` и
  `row.getClass().getDeclaredFields()` вынести нельзя, и о них правило молчит. Совет зависит от объекта:
  потокобезопасный - в константу, непотокобезопасный (`SimpleDateFormat`, `MessageDigest`) - в локальную
  переменную перед циклом. Переменная, которой в цикле присваивают, от итерации зависит, даже если
  объявлена до него: `while (type != null) { type.getDeclaredFields(); type = type.getSuperclass(); }`.
  Код, работающий при запуске, и циклы повторных попыток не считаются.
  О регулярных выражениях в цикле сообщает jr:239, об `ObjectMapper` на каждый вызов - jr:240.
- **jr:420.** Вызов должен стоять в цикле и выполняться параллельной задачей: в лямбде, отданной
  `CompletableFuture` (`supplyAsync`, `runAsync`, `...Async`) или исполнителю (`submit`, `execute`,
  `invokeAll`), в параллельном стриме, в методе с `@Async` либо в методе, до которого от них доходят
  вызовы. Глубину поиска задает `max-call-depth` (по умолчанию 6: от задачи до генератора обычно идут
  через обработчик и пару сервисов). `execute` и `submit` считаются, только когда получатель похож на пул
  потоков: `transactionTemplate.execute(...)` выполняется в том же потоке. Задача находится и тогда, когда
  ее отдает исполнителю свой метод-обертка (`submit(Supplier<T> task) { return supplyAsync(task, executor); }`)
  либо она сначала лежит в локальной переменной. Одиночный вызов и цикл в обычном методе не считаются.
- **jr:421.** Сортировка отдельным оператором (`Collections.sort`, `Arrays.sort`, `list.sort`) локальной
  коллекции, после которой из нее берут только концы: `get(0)`, `getFirst()`, `get(size() - 1)`,
  `getLast()`, `array[0]`, `array[length - 1]`; обращения к `size()`, `isEmpty()` и `length` не мешают.
  Если отсортированную коллекцию обходят, возвращают, передают дальше или берут элемент из середины,
  находки нет. Параметр и поле не считаются: отсортированными их может ждать вызывающий код.
  О том же в стримах (`sorted().findFirst()`) сообщает jr:74.
- **jr:422.** Размер задан числом или константой и не меньше порога `max-threads` (по умолчанию 32):
  `Executors.newFixedThreadPool(100)`, `new ThreadPoolExecutor(10, 200, ...)`, `new ForkJoinPool(64)`,
  `executor.setCorePoolSize(50)`. Размер от `availableProcessors()` и из настроек находкой не является.
  В файлах настроек проверяются `spring.task.execution.pool.*`, `spring.task.scheduling.pool.size` и свои
  свойства, названные как пул потоков (`parallel.executor.threads-count`); уверенность у них «подозрение».
  Потоки веб-сервера (`server.tomcat.threads.max`), пулы соединений и профили разработки не считаются.
  Для задач, которые ждут ввода-вывода, большой пул уместен - поэтому уровень находки MINOR.

  клиенты JDK, Apache и OkHttp), по интерфейсу Feign или Spring HTTP Interface, а без типа - по имени
  объекта (`s3Client`, `ossClient`, `registryClient` - тоже сетевые вызовы). Вызов ищется и в методах, которые
  вызываются из цикла, на глубину `max-call-depth` (по умолчанию 3). Не считаются: цикл повторных попыток,
  ожидание (`while` или `do` с паузой: `while (WAITING.contains(state)) { sleep(10); state = getStatus(); }`),

- **jr:428.** Проверяются только файлы, которые импортируют `reactor.core.publisher`: `block()` у
  `WebClient` в приложении на Spring MVC - обычный вызов. HTTP-клиент считается блокирующим, только если он
  известен (по типу либо по имени `restTemplate`, `restClient`, `httpClient`, `feign`): `ChatClient` и подобные
  по одному имени сюда не попадают. Находка есть, когда блокирующий вызов стоит в
  лямбде оператора Reactor (`map`, `flatMap`, `doOnNext`, `subscribe`, `fromCallable` и других) в реактивной цепочке (цепочка начинается с `Mono` / `Flux`, содержит оператор, который
  есть только у них, или возвращается из метода с типом `Mono` / `Flux`) либо прямо в теле метода, который
  возвращает `Mono` / `Flux`. Не считаются: цепочка с `subscribeOn` / `publishOn` (работа увезена в другой

  реактивный репозиторий (`ReactiveCrudRepository`, `R2dbcRepository` и другие), результат вызова,
  который `flatMap` получает как `Publisher`, тесты и код запуска.
- **jr:429.** Ошибиться в сторону `readOnly` нельзя - запись в такой транзакции не сохранится. Поэтому

  запись (`save`, `delete`, `update`, `persist`, `flush`, `publishEvent`, `send` и подобные), чтение с
  блокировкой (`findByIdForUpdate` в имени метода или вызова, `FOR UPDATE` в тексте запроса, `@Lock`), запись
  в тексте запроса (`DELETE ... RETURNING` через `queryForList`), пишущее имя самого метода (`removeAll...`), метод
  репозитория с `@Modifying`, запись в поле (`this.stock -= quantity` в методе сущности), неразобранный вызов
  не-геттера у своей переменной (`product.take(quantity)`), вызов другого бина, которого нет в графе вызовов,
  и метод с `REQUIRES_NEW`. Не проверяется метод, в комментарии к которому сказано про ведущую базу или
  реплику: транзакция там нужна, чтобы запрос ушел на ведущую базу, а `readOnly` отправит его на реплику. Маппер MapStruct только перекладывает поля и находке не

- **jr:430.** Только уровни `debug` и `trace`: в рабочей среде они выключены почти всегда. Дорогим

## Контейнер Spring в коде приложения

Класс, который сам достает бины из `ApplicationContext` или `BeanFactory`, нарушает инверсию управления:
вместо того чтобы получать зависимости от контейнера, он ищет их сам (Service Locator). Зависимость не видна
в конструкторе, класс нельзя создать в тесте без контекста, а ошибка в имени или типе бина обнаружится при
вызове, а не при старте приложения.

| Правило | Что находит | Уровень |
|---|---|---|
| jr:164 | `getBean`, `getBeansOfType`, `getBeanProvider`, `getBeansWithAnnotation`, `autowireBean`, `createBean` и подобные вызовы у контейнера | MINOR |
| jr:423 | `ApplicationContext` или `BeanFactory` в статическом поле — держатель контекста (`SpringContextHolder.getBean(...)`) | MAJOR |

- **jr:164.** Контейнер узнается по объявленному типу (`ApplicationContext`, `BeanFactory`,
  `AutowireCapableBeanFactory` и их наследники), по вызову `getApplicationContext()` /
  `getAutowireCapableBeanFactory()`, по статическому вызову через имя класса (`SpringContext.getBean(...)`),
  а если тип неизвестен — по имени (`applicationContext`, `beanFactory`, `ctx`). Совет зависит от вызова:
  новый экземпляр prototype-бина и необязательный бин — `ObjectProvider<T>`; выбор реализации по имени,
  вычисленному во время работы, — внедренная `Map<String, T>`; все реализации — `List<T>`; `autowireBean`
  и `createBean` — сделать объект бином либо передать зависимости явно. Не считаются: классы конфигурации
  (`@Configuration`, `@AutoConfiguration`, `@SpringBootApplication`), методы с `@Bean`, `main`, части
  настройки контейнера (`BeanPostProcessor`, `BeanFactoryPostProcessor`, `ImportBeanDefinitionRegistrar`,
  `FactoryBean`, `ApplicationContextInitializer`), сам держатель контекста и тесты. Сообщения о контексте,
  который используют для `publishEvent`, `getEnvironment` или `getMessage`, нет: это не поиск бинов.
- **jr:423.** Статическое поле с контейнером делает бины доступными отовсюду, в том числе из сущностей,
  утилит и объектов, созданных через `new`. До запуска контекста поле равно null, а в тестах, где поднято
  несколько контекстов, указывает на последний. Главный класс с `@SpringBootApplication`, который держит
  контекст, чтобы перезапустить приложение, не считается. Вызовы `getBean` внутри самого держателя jr:164
  не показывает — находка одна, на поле.

## Доступ и безопасность запросов

| Правило | Что находит |
|---|---|
| jr:378 | правило доступа Spring Security, перекрытое более общим правилом выше |
| jr:379 | обработчик `GET` меняет данные в БД |
| jr:380 | пароль, токен или ключ в адресе запроса: `@PathVariable`, `@RequestParam` |
| jr:381 | версия библиотеки с известной уязвимостью |
| jr:382 | запись берется по идентификатору из запроса без проверки владельца |
| jr:452 | данные запроса кладутся в HTTP-сессию без проверки (CWE-501) |

- **Адрес может быть объявлен в интерфейсе.** jr:379, jr:380, jr:382 и jr:385 понимают контроллер, который
  реализует интерфейс с `@GetMapping` и `@PathVariable`: аннотации берутся оттуда. Интерфейс HTTP-клиента
  (`@FeignClient`, `@HttpExchange`) обработчиком не считается.
- **jr:378** сравнивает шаблоны внутри одной настройки `authorizeHttpRequests` / `authorizeRequests`:
  `/api/**` охватывает `/api/admin/**`, `anyRequest()` охватывает все. Правило для одного HTTP-метода
  не охватывает остальные. Одинаковый доступ у обоих правил находкой не считается; шаблоны со звездочкой
  в середине и заданные константой не сравниваются. Находка «подтверждена».
- **jr:379** ищет запись в самом обработчике и в методах, которые он вызывает (`max-call-depth`):
  `save`, `delete...` репозитория, `persist` / `merge` / `remove` у `EntityManager`, `update` у
  `JdbcTemplate`, `save` / `remove` у `DataManager`. Не считаются запись в журнал (репозиторий со словом
  `audit`, `log`, `history`, `stat`, `event`, `visit`, `session`, `token` в имени) и обработчики, которые
  открываются по ссылке: `confirm`, `verify`, `activate`, `unsubscribe`, `callback`, `oauth`, `logout`.
- **jr:380.** `@RequestParam` проверяется у `GET`, `DELETE` и `@RequestMapping` без метода: у `POST`
  параметр может прийти из тела формы. `@PathVariable` — у любого метода. Имя оценивается так же, как
  в остальных правилах о секретах: `tokenType` и `passwordHash` секретом не считаются.
- **jr:381.** Список встроенный, сеть не нужна: Log4Shell (`log4j-core` до 2.17.1), Log4j 1.x,
  Text4Shell (`commons-text` 1.5 – 1.9), SnakeYAML до 2.0, Spring4Shell (Spring Framework 5.3.0 – 5.3.17
  и 5.2.0 – 5.2.19, Spring Boot 2.5.0 – 2.5.11 и 2.6.0 – 2.6.5), Spring Cloud Function и Gateway,
  `commons-collections` до 3.2.2, `fastjson` до 1.2.83, H2 до 2.1.210, драйвер PostgreSQL до 42.2.25
  и 42.3.0 – 42.3.1, XStream до 1.4.18. Проверяются версии, записанные в `pom.xml` и `build.gradle`,
  в том числе через `${свойство}`; библиотека без версии (ее задает родитель) и библиотека только для
  тестов пропускаются. Это не замена полноценной проверке зависимостей: в списке только громкие
  уязвимости с выполнением чужого кода. Находка «подтверждена», уровень — `CRITICAL`.
- **jr:382** — подозрение: проверка может стоять в фильтре или в самом запросе. Находка нужна, когда
  сошлось все: в проекте есть аутентификация; обработчик без `@PreAuthorize` / `@Secured` и ничего
  не знает о пользователе (нет `Principal`, `Authentication`, `SecurityContextHolder`, слов `owner`,
  `permission`, `AccessDenied`); идентификатор из запроса уходит в `findById` / `deleteById` — прямо
  или через сервис, который тоже не знает о пользователе; у сущности есть поле владельца (`user`,
  `owner`, `account`, `customer`, `client`, `author`, `tenant`, `createdBy` и их `...Id`).
- **jr:452.** `setAttribute(name, value)` и `putValue(name, value)` у `request.getSession()`, `HttpSession`
  или переменной `session`, когда в имя атрибута или значение прослежены данные клиента. Код, который потом
  читает сессию, считает ее содержимое установленным сервером, и клиент подменяет идентификатор,
  роль или признак пройденной проверки. Значение, приведенное к числу или проверенное по списку
  допустимых, находкой не считается.

## Ловушки в выражениях и настройках

| Правило | Что находит |
|---|---|
| jr:393 | `(int) Math.random() * n` — приведение к целому раньше умножения, результат всегда ноль |
| jr:394 | результат `compareTo` сравнивается с `1` или `-1` вместо сравнения с нулем |
| jr:395 | настройки, которые прячут ошибки: `enable_lazy_load_no_trans`, `allow-circular-references`, `allow-bean-definition-overriding` |

- **jr:393.** Находка — приведение к `int`, `long`, `short`, `byte`, `char` самого `Math.random()` либо
  `random.nextDouble()` / `nextFloat()` без границ. Произведение в скобках — `(int) (Math.random() * n)` —
  правильная запись. Находка «подтверждена».
- **jr:394.** `compareTo`, `compareToIgnoreCase` и `comparator.compare(a, b)` обязаны вернуть только знак:
  у строк, дат и перечислений это разность, а не единица. Проверяются `== 1`, `== -1`, `!= 1`, `!= -1`;
  в сообщении сказано, чем заменить. Не считаются `BigDecimal`, `BigInteger` и числовые обертки
  (`Integer.compare`, `x.compareTo(y)` для `Integer`, `Long`): они возвращают ровно -1, 0 или 1.
- **jr:395.** Каждая из настроек со значением `true` — отдельная находка:
  `spring.jpa.properties.hibernate.enable_lazy_load_no_trans` (ленивая связь вне транзакции молча
  открывает новое соединение на каждое обращение), `spring.main.allow-circular-references` (бин из цикла
  получает неготовую зависимость), `spring.main.allow-bean-definition-overriding` (бин с тем же именем
  молча заменяет другой). Настройки тестов и профилей разработки не считаются: подмена бинов там —
  обычный прием.

## Запрос, который заканчивается ошибкой сервера или тишиной

| Правило | Что находит |
|---|---|
| jr:397 | перечисление, UUID или дата разбираются из данных запроса без обработки ошибки |
| jr:398 | `catch`, который вместо ошибки возвращает `null`, пустой `Optional` или пустую коллекцию |
| jr:399 | необязательный параметр запроса (`required = false`) с типом-примитивом |
| jr:400 | событие для `@TransactionalEventListener` публикуется вне транзакции |

- **jr:397.** Проверяются `Status.valueOf(text)`, `Enum.valueOf(Status.class, text)`, `UUID.fromString(text)`
  и `parse(text)` у `LocalDate`, `LocalDateTime`, `Instant` и других типов `java.time`. Находка есть, только
  когда строка пришла из запроса: это отслеживается через переменные, геттеры и вызовы методов, как у правил
  о данных извне. Числа проверяет jr:114. Правило молчит, если ошибку уже ждут:
  разбор стоит в `try` с подходящим `catch`; в проекте есть `@ExceptionHandler` для
  `IllegalArgumentException` (для дат — `DateTimeParseException`); значение проверено заранее —
  `EnumUtils.isValidEnum`, перебор `Status.values()`, `@Pattern` на поле запроса либо вызов проверки
  (`validator.validate(request)`, `verify...`, `check...`) перед разбором. Проверка должна стоять на каждом
  пути к разбору: если один обработчик проверяет запрос, а другой передает его в тот же преобразователь
  без проверки, находка остается.
- **jr:398.** Сбой становится неотличим от ответа «ничего нет». Не считаются: `catch (Exception)` — его
  показывает jr:23; исключения «не нашлось» (`...NotFound...`, `NoResult...`, `NoSuchElement...`) и
  «не разобралось» (`NumberFormatException`, `DateTimeParseException`, `IllegalArgumentException`) — там
  пустое значение и есть правильный ответ; `catch` с пробросом; метод с `@Nullable`; `return false` —
  признак успеха вызывающий код проверяет сам; настоящее значение по умолчанию (`Config.defaults()`).
- **jr:399.** Проверяются `@RequestParam`, `@RequestHeader`, `@CookieValue`, `@PathVariable` и подобные.
  С `defaultValue` и с типом-оберткой (`Integer`, `Boolean`) параметр `null` переживает. Находка
  «подтверждена».
- **jr:400.** Слушатель с `@TransactionalEventListener` без активной транзакции не вызывается, и ошибки при
  этом нет. Тип события берется из параметра слушателя, место публикации — `publishEvent(new OrderPaid(...))`
  или `publishEvent(event)`; наследник события попадает к тому же слушателю. Транзакция считается открытой,
  если `@Transactional` стоит на методе с публикацией или на одном из тех, кто его вызывает
  (`max-call-depth`), либо публикация идет внутри `transactionTemplate.execute(...)`. Слушатель
  с `fallbackExecution = true` и обычный `@EventListener` транзакции не ждут.

## Где правила молчат: контекст кода и знания о проекте

Одно и то же действие в разных местах значит разное. Чтобы не сообщать о том, что ошибкой не является,
правила учитывают, в каких обстоятельствах выполняется код, и то, что уже известно о проекте.

### Контекст кода

| Контекст | Как узнается | Что в нем не считается находкой |
|---|---|---|
| Запуск приложения | статическая инициализация; конструктор и поля бина-одиночки; `@Bean`, `@PostConstruct`, `afterPropertiesSet`, `CommandLineRunner.run`, слушатель события запуска; закрытые методы, которые вызываются только оттуда | `toMap` без функции слияния (jr:49): повтор ключа при запуске — ошибка настройки, и упасть сразу правильно. `throws Exception` у метода, который вызывает контейнер (jr:190) |
| Обработка ошибки | блок `catch`; `warn` и `error` под условием внутри цикла | запись в лог в цикле (jr:94): это сообщение об ошибке, а не поток записей о ходе работы |
| Цикл повторных попыток | счетчик или предел назван попыткой (`attempt`, `retry`, `maxTries`) либо `try` в теле цикла заканчивается `return` / `break`, а `catch` идет на следующий круг | запрос к БД в цикле (jr:63) и запись в лог в цикле (jr:94): итерации — это попытки, а не элементы данных |
| Граница задачи | метод с `@Scheduled`, `@Async`, `@KafkaListener` и подобными, `run()` потока, фильтр, `main`; лямбда, отданная исполнителю; `try` прямо в теле цикла, который обрабатывает элементы по одному | `catch (Exception)` без повторного выброса (jr:23) — при условии, что исключение не пропало |

Уточнения:

- **Широкий `catch` на границе задачи** не считается находкой, только если пойманное исключение передано дальше
  целиком — в лог, обработчику, в результат. `log.warn("...", e.getMessage())` стек теряет, и находка остается.
- **Попытки внутри перебора данных** по-прежнему умножаются на число элементов: такой запрос находкой считается.
- **`info` под условием и `warn` на каждом элементе** в цикле находкой остаются: первое сообщает о ходе работы,
  второе пишется для каждого элемента.
- **Конструктор обычного класса** запуском не считается: его объекты создают во время работы.
- **Метод функционального интерфейса** (один абстрактный метод либо `@FunctionalInterface`) может объявлять
  `throws Exception`: он обязан принять любую лямбду.
- Тем же признаком запуска пользуются jr:360 и jr:361: настройка объекта при запуске и во время работы —
  разные случаи.

### Тесты и код приложения

Правила о производительности, безопасности, датах и устойчивости к `null` написаны для кода приложения.
В тестах они сообщают о том, что ошибкой не является: тест готовит данные запросом в цикле, вызывает
`optional.get()` без проверки, а упавший тест и есть нужный исход. Поэтому в каталогах тестов — и в коде,
и в файлах настроек — остаются находки только правил для тестов (jr:141 – jr:143, jr:198, jr:344 – jr:348
и подобных).

Тестами считаются каталоги `test`, `tests`, `javatests` (Bazel), `integrationTest`, `integration-test`,
`testFixtures`, а также наборы исходников Gradle рядом с `src/test`, имя которых кончается на `Test`:
`src/internalClusterTest`, `src/javaRestTest`, `src/yamlRestTest`, `src/heapPressureTest`. Пакет с таким же
именем внутри `src/main` (`com.shop.loadTest`) — обычный код.

```properties
# вернуть прежнее поведение: все правила проверяют и тесты
zond.scan.test-rules-only=false
```

Тесты при этом по-прежнему читаются: по ним видно, что класс или метод используется. Чтобы не читать их
вовсе, есть `zond.scan.skip-tests=true`.

### Каталоги сборки

Java-файлы из каталогов `build`, `target` и `out` читаются: по сгенерированному коду видно, что класс или
метод используется. Но находки в них не показываются: править там нечего, а копия исходника, которую
кладет туда форматтер или генератор, дала бы каждую находку дважды. Каталог с таким именем внутри `src` —
обычный пакет, и он проверяется как всегда.

Так же скрываются находки в чужом коде, вложенном в проект: каталоги `third_party`, `third-party`,
`thirdparty`, `third_parties`, `vendor`, `vendored` (в Bazel это четверть всех находок).
Код из них читается: по нему видно, что класс или метод используется. Каталог `vendor` внутри `src` — пакет
проекта (`com.shop.vendor`), и он проверяется.

И так же — в сгенерированном коде: на классе стоит `@Generated` либо в шапке файла до тела класса написано
«auto-generated», «@generated», «Generated by ...», «DO NOT EDIT» (кодеки протокола Hazelcast, классы protobuf
и ANTLR). Его правят через генератор, а изменения, внесенные вручную, пропадут при следующей генерации.

MyBatis Generator часто настраивают без комментариев (`suppressAllComments`), и его классы узнаются по
устройству: `XxxExample` с вложенным классом `GeneratedCriteria`, интерфейс `XxxMapper`, в котором только
методы генератора (`countByExample`, `selectByPrimaryKey`, `updateByExampleSelective` и подобные, не меньше
четырех), и модель с `toString`, где есть `"Hash = "`. В mall это убрало 7 200 находок из 7 800.

### Знания о проекте

- **`@Value` без значения по умолчанию** (jr:136). Если свойство задано в основном файле настроек
  (`application.properties`, `application.yml` без профиля), оно есть в любом окружении, и находки нет.
  Находка остается, когда свойство задано только в файлах профилей или в настройках тестов — в сообщении
  названы эти файлы — и когда ключ выглядит как переменная окружения (`DB_HOST`). О свойстве, которого нет
  ни в одном файле, сообщает jr:301: дважды об одной строке правила не говорят. Если файлы настроек
  в проверку не попали, правило работает по-старому и отмечает каждый `@Value` без значения по умолчанию.
- **Коллекция без `@Size` во входном DTO** (jr:111). Входным считается класс, в который действительно
  разбирается запрос или сообщение: параметр обработчика с `@RequestBody`, `@ModelAttribute`, `@RequestPart`
  в контроллере (или в интерфейсе, который контроллер реализует), параметр метода с `@KafkaListener` и
  подобными — вместе с классами его полей и предками. Запрос, который приложение само отправляет другому
  сервису (`@FeignClient`, DTO клиентов внешних API), и ответы сюда не попадают, как бы они ни назывались.
  `byte[]` и `char[]` коллекцией не считаются. Если в проверку не попал ни один контроллер, правило судит
  по имени класса, как раньше, и ставит уверенность «подозрение».
- **Свойство, которое нигде не читается** (jr:302). Значение, перенесенное на несколько строк через `\`,
  читается как одно свойство. Свойство считается прочитанным, если его имя встречается в коде, в значении
  другого свойства либо в XML и манифестах проекта (`<springProperty source="...">` в logback). Одно и то же
  свойство в файлах нескольких профилей — одна находка. Если из раздела настроек (первое слово ключа) код
  не читает ничего, раздел, скорее всего, принадлежит библиотеке, и находка получает уверенность
  «подозрение»; у остальных она «вероятно».
- **Библиотека.** Если в проекте нет ни `main`, ни `@SpringBootApplication`, это библиотека: открытые
  классы и их открытые и защищенные методы — ее API, ими пользуются проекты, которые ее подключают.
  jr:205 и jr:206 считают их используемыми и сообщают только о закрытом и package-private коде.
- **Одноименные классы.** Тип параметра ищется с учетом импортов и пакета файла: два класса `OrderRequest`
  в разных пакетах различаются, а класс библиотеки (`Update` из чужого API) не подменяется одноименным
  классом проекта. Так же ищется предок класса во всех правилах, которым он нужен.

## Цикломатическая сложность

Правило jr:193 считает, сколько независимых путей выполнения есть в методе или конструкторе, и сообщает,
когда их больше допустимого. Один путь есть всегда; по одному добавляют:

| Конструкция | Пример |
|---|---|
| условие | `if`, каждый `else if` |
| цикл | `for`, `for-each`, `while`, `do-while` |
| обработчик исключения | каждый `catch` |
| ветка выбора | каждый `case` в `switch`; `default` не считается, `case 2, 3` — одна ветка |
| тернарный оператор | `a > 0 ? x : y` |
| логическая связка | каждое `&&` и `\|\|` в условии |

- Ветвления внутри лямбды относятся к методу, в котором она записана.
- Методы анонимного и локального класса, объявленных внутри метода, считаются отдельно: к внешнему методу
  их ветвления не прибавляются.
- Тесты не проверяются.

Порог по умолчанию — 10. Он меняется параметром правила:

```properties
zond.rule.jr-193.max-complexity=15
```

В сообщении названа сама сложность — `Цикломатическая сложность метода 'register' - 21 при допустимой 10`, —
так что самые запутанные методы видны сразу.

## Только измененные файлы

Чтобы видеть находки лишь в том, что вы правили, а не во всем проекте:

```properties
zond.scan.changed-only=true
```

То же задается аргументом `--changed-only` и пунктом «Только измененные файлы» в настройках меню.
Откуда zond узнает, что изменилось, зависит от папки:

| Папка | Откуда берутся изменения | С чем сравнивается |
|---|---|---|
| лежит в репозитории git | у самого git | с `HEAD` либо с веткой, тегом или коммитом из `zond.scan.changed-since` |
| git нет (или он не установлен) | из хешей файлов, которые zond запоминает сам | с прошлой проверкой этой папки |

### В репозитории git

```properties
zond.scan.changed-only=true
# с чем сравнивать; без этой строки - с HEAD, то есть берется только незакоммиченное
zond.scan.changed-since=origin/main
```

| Сравнение | Что считается измененным |
|---|---|
| с `HEAD` (по умолчанию) | измененное и еще не закоммиченное, а также новые файлы, которые git пока не отслеживает |
| с веткой, тегом или коммитом | все, что изменилось с места, где текущая ветка отошла от заданной: закоммиченное, незакоммиченное и новые файлы |

zond запускает `git diff` и `git ls-files` в сканируемой папке; файлы из `.gitignore` в список не входят.
Аргумент `--changed-since=origin/main` задает точку отсчета и сам включает режим. Ветки или коммита
с таким именем нет — это ошибка, код завершения 2.

### Без git: по хешам файлов

После проверки zond записывает SHA-256 каждого проверенного файла, а при следующей считает измененным
файл, которого тогда не было либо у которого хеш стал другим. Дата файла не учитывается: ее меняет
и простое копирование проекта, а содержимое остается тем же.

- **Первая проверка идет по всем файлам:** сравнивать еще не с чем. После нее хеши сохраняются,
  и путь к файлу с ними выводится в консоль.
- **Точка отсчета — прошлая проверка в этом режиме.** Каждая такая проверка запоминает хеши заново,
  поэтому находка, которую вы не исправили, при следующем запуске уже не покажется: файл с тех пор
  не менялся. Полная проверка (без режима) хеши не трогает — ею можно посмотреть на проект целиком
  и не сбить точку отсчета.
- **Хеши запоминаются после того, как отчет записан.** Если проверка или запись отчета не удались,
  точка отсчета остается прежней.
- **Хранятся хеши вне проекта:** в `~/.zond/snapshots`, по файлу на каждую сканируемую папку; место
  меняет `zond.scan.snapshot-dir`. Удалите файл — и следующая проверка снова пройдет по всем файлам.
- **Запоминаются только файлы, которые проверялись.** Если тесты были отключены `zond.scan.skip-tests`
  или путь стоял в `zond.scan.exclude`, то после включения такие файлы считаются новыми.
- `zond.scan.changed-since` здесь не используется: сравнивать можно только с прошлой проверкой.

### Чего ждать в обоих случаях

- **Проект читается целиком, показываются находки в измененных файлах.** Правилам, которые строят граф
  вызовов, ищут неиспользуемый код или сверяют сущности со схемой БД, нужен весь проект: на одних
  измененных файлах каждый класс оказался бы «неиспользуемым». Поэтому чтение и разбор занимают столько же
  времени, сколько обычно; быстрее идут только правила, которые смотрят файл сам по себе, — они
  запускаются лишь на измененных файлах.
- **Находка в неизмененном файле не показывается,** даже если ее вызвала ваша правка: удалили последний
  вызов метода — метод стал неиспользуемым, но его файл вы не трогали. Перед слиянием большой ветки стоит
  прогнать проверку целиком.
- **Удаленные файлы** в список измененных не входят: проверять в них нечего.
- **Изменений нет** — проект не читается вовсе, отчет пишется пустой, код завершения 0.
- В отчете появляется строка «Находки показаны только в измененных файлах: N» — чтобы пустой отчет
  не приняли за чистый проект. N — число измененных файлов среди тех, что zond проверяет.

## Параллельное сканирование

```properties
zond.scan.threads=4
```

| Значение | Как идет сканирование |
|---|---|
| `1` (по умолчанию) | в одном потоке: файлы разбираются и правила запускаются по очереди |
| `0` | потоков столько, сколько ядер у процессора |
| `N` | ровно `N` потоков |

В несколько потоков идут и разбор файлов, и запуск правил. Отчет от числа потоков не зависит: находки
всегда собираются в порядке правил. На 12 ядрах сканирование крупного проекта быстрее примерно
на треть — заметная часть времени уходит на разрешение типов, которое выполняется по очереди.
То же задается аргументом `--threads=...` и пунктом «Потоки сканирования» в настройках меню. Допустимо
целое число от 0 до 128. Иное значение в аргументе или в `app.properties` останавливает запуск с кодом 2,
а в меню ввод спрашивается заново.

## Исключение путей

```properties
zond.scan.exclude=generated, src/main/java/legacy, *Dto.java, **/migration/**
```

Шаблон сверяется с путем файла от корня сканирования:

| Шаблон | Что исключает |
|---|---|
| `generated` | каталог или файл с таким именем на любой глубине, со всем содержимым |
| `src/main/java/legacy` | этот каталог со всем содержимым |
| `*Dto.java` | файлы по имени в любом каталоге |
| `**/migration/**` | путь по шаблону: `*` — часть имени, `**` — любые каталоги, `?` — один символ |

Исключенные файлы не разбираются вовсе - ни правилами, ни при разрешении типов. То же задается
аргументом `--exclude=...` и пунктом «Исключенные пути» в настройках меню.

## Как скрыть находку

Комментарием прямо в проверяемом коде:

```java
int port = 8080; // zond:ignore jr:40        - на этой строке

// zond:ignore jr:40, jr:104                 - на следующей строке
// zond:ignore                               - все правила на следующей строке
// zond:ignore-file jr:40                    - во всем файле
```

Вместо кода можно писать имя правила (`MagicNumberRule`). В файлах настроек то же самое пишется
после `#`, в SQL — после `--`, в `pom.xml` — в `<!-- zond:ignore -->`. Число скрытых находок показывается в шапке отчета.

## Настройка отдельных правил

```properties
zond.rule.jr-193.max-complexity=15
zond.rule.LongMethodRule.max-lines=80
zond.rule.jr-36.level=INFO
```

- **Правило** задается именем класса либо кодом через дефис: `jr-193`, а не `jr:193`. Двоеточие в ключе
  `.properties` отделяет значение, поэтому с ним настройка не прочитается.
- **`level`** есть у каждого правила: меняет уровень находок в отчете и учитывается порогом `min-level`.
- **Пороги** есть у отдельных правил:

| Правило | Параметр | По умолчанию |
|---|---|---|
| jr:104 много параметров у метода | `max-parameters` | 4 |
| jr:112 длинный метод | `max-lines` | 50 |
| jr:113 глубокая вложенность | `max-depth` | 4 |
| jr:144 большой класс | `max-lines`, `max-methods` | 500, 30 |
| jr:145 много зависимостей у бина | `max-dependencies` | 7 |
| jr:193 цикломатическая сложность | `max-complexity` | 10 |
| jr:195 повторяющиеся строковые литералы | `min-occurrences`, `min-length` | 3, 5 |
| jr:256 методы с одинаковым телом | `min-lines` | 10 |
| jr:213 несколько записей в БД без транзакции | `max-call-depth` | 3 |
| jr:57 HTTP-вызов в транзакции, jr:58 файловая операция в транзакции, jr:63 запрос к БД в цикле, jr:8 запись в readOnly-транзакции, jr:17 незакрытый ресурс, jr:427 HTTP-вызов в цикле, jr:429 транзакция без readOnly | `max-call-depth` | 3 |
| jr:420 `UUID.randomUUID()` в цикле параллельной задачи | `max-call-depth` | 6 |
| jr:422 пул потоков постоянного размера | `max-threads` | 32 |

### Глубина поиска по вызовам

Параметр `max-call-depth` есть у правил, которые ищут проблему не только в самом методе, но и в методах,
которые он вызывает (jr:8, jr:17, jr:57, jr:58, jr:63, jr:213, jr:365, jr:368, jr:379, jr:400, jr:420, jr:427, jr:429), и у правил,
которые прослеживают данные
извне (jr:18, jr:87, jr:207 – jr:212 и другие). Его можно задать сразу для всех:

```properties
zond.max-call-depth=5
```

и отдельно для правила — такое значение важнее общего:

```properties
zond.max-call-depth=5
zond.rule.jr-63.max-call-depth=1
```

| Что задано | Какая глубина действует |
|---|---|
| ничего | значение правила по умолчанию: 3 у правил о цепочках вызовов, 4 у правил о данных извне |
| только `zond.max-call-depth` | оно, для всех правил с этим параметром |
| `zond.max-call-depth` и `zond.rule.<правило>.max-call-depth` | у этого правила — свое, у остальных — общее |

`0` отключает поиск по вызовам: проверяется только тело самого метода. Глубина — это не «точность»:
она решает, насколько длинную цепочку вызовов анализ пройдет. Больше глубина — больше найденных цепочек;
ложных срабатываний от нее не становится ни больше, ни меньше. Если до операции ведет несколько путей,
в сообщении показан кратчайший. Время сканирования от глубины почти не зависит: методы, до которых
анализ уже дошел, повторно не разбираются.

Актуальный перечень параметров с текущими значениями показывает пункт меню «Список правил»: у правила
там выводится готовая строка для `app.properties`.

Ошибка в этих настройках (неизвестное правило или параметр, не число, неизвестный уровень) останавливает
запуск с кодом 2 — иначе опечатка молча оставила бы прежний порог.

## Разрешение типов

Zond определяет настоящий тип выражения — по другим файлам проекта и по JDK. Это позволяет отличить
репозиторий от строки с именем `userDao`, собственный класс `Files` от `java.nio.file.Files`,
наследника `ReentrantLock` от постороннего класса.

Типы из зависимостей (Spring, JPA) без самих библиотек остаются неизвестными. Чтобы они разрешались,
укажите jar-файлы проверяемого проекта:

```properties
zond.scan.classpath=C:/projects/shop/libs;C:/projects/shop/extra/driver.jar
```

Папки просматриваются рекурсивно. Если тип определить не удалось, правило судит по именам
(`userRepository`, `restTemplate`, `log`) — сканирование от этого не падает.

Код, который появляется только при сборке, в исходниках не виден. Для Lombok он восстанавливается
по аннотациям:

- геттеры от `@Getter`, `@Data`, `@Value` и сеттеры от `@Setter`, `@Data`, включая
  `@Accessors(chain = true)` и `@Accessors(fluent = true)`;
- `User.builder()...build()` и `user.toBuilder()...build()` от `@Builder` / `@SuperBuilder`;
- методы `withX(...)` от `@With`;
- поле `log` от `@Slf4j`, `@Log4j2` и других аннотаций логирования;
- `val` — тип берется из инициализатора;
- `@Cleanup` — ресурс считается закрытым.

Сеттер от Lombok в singleton-бине считается изменением его состояния. Остальное (`@Delegate`,
`@SneakyThrows`, настройки из `lombok.config`) не учитывается.

### Библиотеки находятся автоматически

Для проекта Maven библиотеки указывать не нужно: zond читает его `pom.xml` и берет jar-файлы из локального
репозитория (`~/.m2/repository`), куда их уже скачал Maven при сборке. Сам Maven не запускается.

```
Библиотеки проекта: найдено 218 в C:\Users\me\.m2\repository; не найдено 1: org.springframework.data:spring-data-redis:3.3.1
```

- **Версии** берутся оттуда же, откуда их взял бы Maven: из самой зависимости, из `dependencyManagement`
  проекта, его родительских `pom.xml` и подключенных BOM — так задает версии `spring-boot-starter-parent`.
  Если версию узнать не удалось, берется самая свежая из скачанных.
- **Зависимости зависимостей** читаются из их pom-файлов в репозитории; тестовые и необязательные
  зависимости библиотек не подключаются.
- **Многомодульный проект:** читаются все `pom.xml` в сканируемой папке, модули друг для друга
  библиотеками не считаются.
- **«Не найдено»** означает, что библиотеки нет в локальном репозитории: проект еще не собирали на этой
  машине либо она лежит в недоступном репозитории. Сканирование продолжается, типы из нее остаются
  неизвестными. Чтобы они появились, соберите проект (`mvn compile`).
- Библиотеки из `zond.scan.classpath` добавляются к найденным.

Это упрощенное повторение работы Maven: исключения (`exclusions`), профили и диапазоны версий не учитываются.
Для разрешения типов этого достаточно.

Для проекта Gradle так же читаются `build.gradle` и `build.gradle.kts` всех модулей, а jar-файлы берутся из кэша
Gradle (`~/.gradle/caches/modules-2/files-2.1` либо тот же каталог внутри `GRADLE_USER_HOME`) и из
`~/.m2/repository`. Сам Gradle не запускается.

- Понимаются записи `implementation 'группа:имя:версия'`, `implementation("группа:имя:версия")`,
  `compileOnly group: 'g', name: 'n', version: 'v'` и ссылки на каталог версий `implementation libs.spring.web`
  (`gradle/libs.versions.toml`, в том числе `version.ref`). Конфигурации `implementation`, `api`, `compileOnly`,
  `runtimeOnly`, `compile`, `provided`; тестовые (`testImplementation` и другие) пропускаются.
- Версии из свойств (`$springVersion`, `${springVersion}`) берутся из `gradle.properties` и простых присваиваний
  в скрипте (`ext.springVersion = '6.1.0'`, `val springVersion = "6.1.0"`). Зависимость без версии получает ее из
  BOM: `platform('группа:имя:версия')` и плагина `org.springframework.boot` с версией (`spring-boot-dependencies`).
- Зависимости зависимостей читаются из их pom-файлов в том же кэше.

Скрипты Gradle — это код, и все его возможности здесь не повторить: зависимость, координаты которой вычисляются
в коде, останется ненайденной. В сообщении «Библиотеки проекта» тогда будет указано, чего не хватило.

Отключается настройкой `zond.scan.auto-classpath=false` либо аргументом `--auto-classpath=false`. Если
репозиторий лежит не в `~/.m2/repository` и не указан в `~/.m2/settings.xml`, задайте его в
`zond.scan.maven-repository`.

## Анализ хода выполнения

Часть правил смотрит не на отдельную строку, а на то, как выполняется программа.

- **Цепочки вызовов.** HTTP-вызов или запись в файл внутри транзакции и запрос к БД в цикле находятся,
  даже если операция спрятана в вызванном методе другого класса. Находка ставится на вызов, который
  к ней ведет, с указанием пути: `(через вызов notifyClient -> send)`. Глубину поиска задает параметр
  `max-call-depth`; `0` отключает поиск по цепочке. Вызов метода интерфейса ведет к его реализациям
  в проекте. В `@Async`-методы поиск не заходит: они выполняются вне транзакции вызывающего.
- **Запись в readOnly-транзакции.** `save` / `delete` / `update` находятся и в методах, которые вызывает
  метод с `@Transactional(readOnly = true)`: они выполняются в той же транзакции. Метод с `REQUIRES_NEW`
  открывает свою транзакцию, поэтому в него поиск не заходит; обычный `@Transactional` присоединяется
  к уже открытой и от записи не спасает.
- **Путь ресурса.** Ресурс прослеживается через методы проекта. Если он отдан методу, который его тоже
  не закрывает, это утечка; если метод закрывает ресурс или передает дальше неизвестному коду — нет.
  Метод, который возвращает открытый ресурс (`return new FileReader(...)`), считается открывающим его
  для вызывающего. Сравнение с `null` и запись в лог закрытием или передачей не считаются.
- **Данные извне.** Для пути к файлу, адреса перенаправления, SQL и других опасных мест прослеживается,
  управляет ли значением кто-то снаружи: от использования назад через переменные, обработку строк и
  параметры методов до источника. Источники:
  - HTTP-запрос: `@RequestParam`, `@PathVariable`, тело запроса, строковый параметр обработчика —
    в том числе когда адрес и аннотации параметров объявлены в интерфейсе, который контроллер реализует;
  - запрос JAX-RS (Jersey, RESTEasy, Keycloak): `@QueryParam`, `@PathParam`, `@FormParam`, `@HeaderParam`,
    `@CookieParam`, `@BeanParam` и параметр без аннотаций у метода с `@POST`, `@PUT`, `@PATCH`, `@DELETE` —
    это тело запроса;
  - запрос сервлета: `getParameter`, `getHeader`, `getQueryString`, а у объекта `HttpServletRequest`
    (или переменной `request` / `req`) еще `getParameterValues`, `getParameterMap`, `getParameterNames`,
    `getHeaders`, `getCookies`, `getReader`, `getInputStream`, `getPart`. У `HttpHeaders` из ответа другого
    сервиса `getHeaders` источником не считается;
  - загруженный файл: `MultipartFile.getBytes()`, `getInputStream()`;
  - сообщение из очереди: параметры методов с `@KafkaListener`, `@RabbitListener`, `@JmsListener`,
    `@SqsListener`, `@MessageMapping`;
  - ответ внешнего сервиса: `RestTemplate.getForObject(...)`, `exchange(...)`, `WebClient...bodyToMono(...)`;
  - свойство объекта, в которое где-то в проекте записали такое значение: `order.setComment(comment)`
    в контроллере и `order.getComment()` в сервисе. Так находятся и данные, сохраненные в сущность.
    Учитывается тип объекта; свойство, в которое данные извне не кладут, источником не считается.
    Значение прослеживается и через конструктор (`new Order(comment)`, в том числе созданный Lombok),
    и через запись: `new OrderRecord(comment)` и `record.comment()`. Геттер, который отдает поле с другим
    именем (`getComment() { return text; }`), сопоставляется с этим полем. Если в этот же объект выше в том же
    методе что-то записали (`draft.setComment("черновик"); ... draft.getComment()`), читается именно это, а не
    то, что пишут в свойство в других местах; объект, созданный здесь же и никуда не переданный, несет только
    аргументы своего конструктора. Свойства объектов JDK (`calendar.setTime(date)`, `thread.setName(name)`)
    данные между методами не передают и не учитываются;
  - результат маппера без тела (MapStruct, библиотека): `mapper.toEntity(dto)` несет то же, что `dto`;
  - параметр лямбды: в `tags.forEach(tag -> ...)` значение `tag` — элемент `tags`.

  Значение проходит и через:
  - **свой метод, который его возвращает:** `bar = decorate(param)`, `new Helper().build(param)`,
    `Utils.wrap(param)`. Разбирается тело метода, а его параметры берут значения из аргументов именно этого
    вызова: `decorate("guest")` рядом с `decorate(param)` данных клиента не несет. Одноименные классы разных
    файлов (внутренний `Test` в каждом сервлете) различаются, как у компилятора: сначала класс своего файла,
    затем импортированный, затем класс своего пакета;
  - **коллекцию и `StringBuilder`:** `sql.append(name)`, `names.add(name)`, `params.put("name", name)`.
    Чтение по известному ключу из карты, собранной в том же методе, несет только положенное под этот ключ:
    `map.get("keyA")` рядом с `map.put("keyB", param)` чист. Для списка, который наполняют `add` и
    `remove(0)` подряд без ветвлений, известно, какой элемент вернет `get(1)`;
  - **массив:** `String[] env = {param}`.

  **Порядок выполнения внутри метода учитывается.** Для каждого чтения переменной считается, какие присваивания
  до него могут дойти (достигающие определения): метод проходится в порядке выполнения, в ветках `if` и `case`
  свое состояние, после развилки состояния сливаются, `return`, `throw`, `break` и `continue` обрывают путь,
  тело цикла проходится, пока множества не перестанут расти, а в `catch` доходит все, что присвоено в `try`.
  Поэтому:
  - `bar = param; bar = "safe"; use(bar)` — только `"safe"`;
  - `if (param == null) { bar = "x"; return; } use(bar)` — присваивание в ветке с `return` не доходит;
  - ветка с условием, известным без запуска, не выполняется: `(7 * 18) + num > 200 ? "safe" : param` при
    `int num = 106`, `if (false)`, `switch ("ABC".charAt(1))` с проваливанием по `case`. Считаются литералы,
    арифметика, константы `final` и локальные переменные, которым больше ничего не присваивают.

  Поля, переменные внешнего метода во вложенном классе и переменные шаблона `instanceof` по порядку не
  отслеживаются: для них учитываются все присваивания в методе, как раньше.

  **Свой метод разбирается один раз.** Для каждого метода и вида места назначения (SQL, HTML, путь, команда)
  считается сводка: есть ли в нем самом источник (`return request.getParameter("name")`) и какие параметры
  доходят до `return`. В месте вызова по сводке проверяются только аргументы этих параметров. Метод, который
  вызывает сам себя, о результате ничего не говорит. Так же один раз считается, что приходит в параметр от
  вызывающих: метод, который вызывают из многих мест, не обходит их заново для каждого чтения параметра.
  Сводка параметра хранится отдельно для каждого вида места назначения и запаса глубины и считается заново, без
  узлов, пройденных тем, кто спросил: ответ не зависит от того, какое правило спросило первым. Если поиск
  оборвала рекурсия (метод передает параметр сам себе), ответ верен только для этого пути и в сводку не идет —
  так же и у сводок `return`.

  **Источники, передающие методы и очистка описаны в справочнике** `taint-library.properties` внутри
  приложения: методы и типы запроса, аннотации параметров, обработчики очередей, ответы HTTP-клиентов, типы без
  данных (`int`, `UUID`), методы приведения, слова в имени метода очистки. Свой фреймворк добавляется файлом того
  же вида:

  ```properties
  # app.properties
  zond.taint.library=taint-library-extra.properties
  ```

  ```properties
  # taint-library-extra.properties
  request-methods=getVertxParam, pathParam
  request-annotations=Header
  sanitizer-words=clean
  ```

  Записи своего файла добавляются к встроенным.

  Значение перестает считаться опасным, если оно:
  - числового типа, дата или `UUID`;
  - приведено к числу, `UUID` или `enum`: `Long.parseLong(id)`, `Status.valueOf(status)`;
  - имеет тип `enum`;
  - проверено на пути к использованию: по списку допустимых (`ALLOWED.contains(sort)`), по шаблону
    (`value.matches(...)`), сравнением с константой — либо помечено `@Pattern` на параметре.
    Учитывается смысл условия: `if (!ALLOWED.contains(sort)) throw ...;` и
    `if (ALLOWED.contains(sort)) { use(sort); }` — проверка, а `if ("admin".equals(role)) return;` — нет:
    дальше идут как раз все остальные значения. Условие с `||`, которое не гарантирует проверку, тоже
    не считается. Проверка свойства объекта — `if (cookie.getName().equals("id"))` — не проверяет другие
    его свойства: `cookie.getValue()` внутри такой ветки остается данными клиента;
  - прошло вызов-утверждение отдельной строкой: `validate(name)`, `requireAllowed(sort)`;
  - прошло метод очистки: `escape...`, `sanitize...`, `validate...`, `normalize...`. Очистка учитывает, куда
    попадает значение: экранирование для HTML (`encodeForHTML`, `htmlEscape`, `escapeHtml`) защищает вывод в
    ответ, но не SQL, путь к файлу и команду и не делает значение проверенным для сессии (jr:452);
    `encodeForSQL` защищает только SQL. Base64 и hex
    (`encodeBase64`, `decodeBase64`, `encodeHex`) не защищают ничего: значение восстанавливается как было.

  Правило о подделке строк лога учитывает только прямой ввод (запрос, файл, сообщение): ответ другого
  сервиса в логе — обычное дело. Для запуска команд источник дописывается в сообщение.
  SQL-инъекция (jr:18, jr:87) — находка, только если в текст запроса прослежены данные клиента. Запрос,
  собранный из констант, значений настроек (`@Value`) и параметров внутренних методов, находкой не
  считается: нарушитель этими значениями не управляет. Сам по себе `Statement` тоже не находка. Запросом
  считается и вызов хранимой процедуры в синтаксисе JDBC: `"{call " + name + "}"`, `"{? = call ...}"`.
  На том же механизме работают правила об SSRF, подделке строк лога, регулярных выражениях, рефлексии,
  выражениях SpEL / XPath / LDAP и выводе в ответ без экранирования (jr:207 - jr:212). Вывод в ответ — это
  `write`, `print`, `println`, `append`, `printf` и `format` у `response.getWriter()`, `getOutputStream()` и
  переменной, в которую их положили.
  Запуск команд (jr:138) проверяется у `Runtime.getRuntime().exec(...)` и у переменной, в которую положили
  `Runtime.getRuntime()`, у `new ProcessBuilder(...)` и `processBuilder.command(...)`. Находка — данные клиента
  в команде, ее аргументах или окружении (`String[] env = {param}; r.exec(args, env)`) либо строка команды,
  собранная из значений, которые могут прийти снаружи, даже если источник не прослежен («подозрение»):
  параметра метода — прямо или через локальные переменные — и поля без `final`. Команда из констант,
  значений настроек (`@Value`) и того, что метод вычислил сам (`cmd = osCommand(); exec(cmd + "safe")`),
  находкой не считается: ее никто снаружи не задает. Как и при прослеживании данных, учитываются только
  присваивания, которые доходят до команды, ветки с известным условием и то, какие аргументы свой метод
  возвращает: `bar = new Test().doSomething(request, param)`, где метод возвращает константу, команду не
  портит.
  Предсказуемый генератор (jr:137) ищется не только по имени вокруг (`token`, `password`, `rememberMe`):
  значение прослеживается по присваиваниям метода, и `float rand = new Random().nextFloat()`, которое
  становится `rememberMeKey` или значением `new Cookie(...)`, — находка с уверенностью «вероятно».
  `random.nextBytes(bytes)` заполняет массив `bytes`: дальше прослеживается он.
- **Секреты.** Имя `password` или `token` само по себе не делает значение секретом. Правила о записи в лог
  (jr:155), `toString()` (jr:154) и сравнении (jr:251) смотрят, что происходит на деле:
  - имя говорит о защите — `encryptedPassword`, `passwordHash`, `maskedToken` — не секрет;
  - значение получено шифрованием или хешированием (`encrypt(...)`, `passwordEncoder.encode(...)`,
    `sha256Hex(...)`) — не секрет; `Base64` и URL-кодирование защитой не считаются;
  - в сообщение попадает не само значение, а его длина, признак наличия (`password != null`) либо
    результат обработки (`mask(token)`) — не находка;
  - свойство, в которое по всему проекту кладут только защищенные значения
    (`entity.setPassword(passwordEncoder.encode(raw))`), секретом не считается: `entity.getPassword()` в логе
    и поле `password` в `toString()` сущности раскроют только хеш. Учитывается тип объекта: у `LoginRequest`
    то же свойство остается секретом;
  - константа с названием вида значения (`SECRET = "Secret"`) секретом не является.
- **Слабый хеш** (jr:106). Находка зависит от того, что хешируется, — это видно по именам вокруг:
  контрольная сумма файла, ключ кэша, ETag, кольцо согласованного хеширования (`ExecutorRouteConsistentHash`) —
  не защита, находки нет; пароль, токен, подпись — вероятная ошибка; иначе остается подозрение.
  Алгоритм в `MessageDigest.getInstance(...)` и `Cipher.getInstance(...)` (jr:149) берется не только из
  литерала: из переменной, которой его присвоили один раз, и из файла настроек самого проекта —
  `props.load(getResourceAsStream("crypto.properties")); props.getProperty("hashAlg", "SHA-256")` с
  `hashAlg=MD5` в `src/main/resources/crypto.properties` — находка. Нет ключа в файле — действует значение по
  умолчанию из вызова; нет самого файла — алгоритм неизвестен.
- **Отключенный CSRF** (jr:107) — не находка, если в той же конфигурации видно, что cookie-сессий нет:
  `SessionCreationPolicy.STATELESS`, `oauth2ResourceServer`, JWT.
- **CORS для любых сайтов**: вместе с `allowCredentials(true)` — подтвержденная находка, без него —
  подозрение: для публичного API это бывает осознанным решением.
- **Значения-заглушки** — `changeme`, `<your-token>`, `xxx`, `REPLACE_ME` — секретом не считаются ни
  в коде, ни в настройках. Слабые, но настоящие пароли (`admin`, `123456`) считаются.
- **JNDI, LDAP и XPath** (jr:339 – jr:341). Находка есть, только если в имя для `lookup`, в фильтр LDAP
  или в выражение XPath попадают данные извне. Фильтр, собранный через `EqualsFilter` и `LdapQueryBuilder`
  либо экранированный `LdapEncoder.filterEncode`, и выражение с переменными XPath находкой не считаются.
- **Загрузка файла** (jr:342). Находка — когда содержимое `MultipartFile` сохраняется, а в методе нет
  обращения ни к типу содержимого, ни к имени файла. Если файл передан в другой метод, правило молчит:
  проверка может стоять там.
- **Копирование свойств в сущность** (jr:343). `BeanUtils.copyProperties(request, entity)` — находка, когда
  источник пришел из запроса, а приемник — класс с `@Entity`. Вызов со списком `ignoreProperties` и
  копирование в обычный объект находкой не считаются.
- **Адрес по `http://`** (jr:359) — находка только для внешнего адреса: `localhost`, частные сети, имена
  без точки (`http://orders:8080`) и внутренние зоны (`.local`, `.svc`, `.internal`) пропускаются, как и
  профили разработки и тестов и заглушки вместо адреса (`sso.test.com`, `example.com`, `http://credit.return.url`).
- **Отключенная проверка SSL** (jr:140). Отключение без условия — находка. Отключение под условием —
  переключатель, и решает значение флага: находка будет, если ветку включает настройка рабочей среды
  (`http.client.verify-hostname=false` в `application.properties`; профили `dev`, `local`, `test` не
  учитываются) либо значение флага по умолчанию (`@Value("${...:true}")`, инициализатор поля). Если флага
  в настройках нет и значения по умолчанию не видно, либо условие сложнее одного флага, находки нет.
- **Проверки на пути.** `list.get(0)`, `optional.get()` и `iterator.next()` считаются защищенными,
  только если проверка охватывает обращение (условие `if`, цикла, `?:`, левая часть `&&`) либо стоит
  выше и обрывает выполнение (`if (list.isEmpty()) return;`). Проверка после обращения или в другой
  ветке защитой не считается.
  Так же проверяются возможный `null` из `Map.get` и `orElse(null)`, `Boolean` в условии, приведение
  `Object` без `instanceof`, индекс без проверки длины и деление на размер коллекции (jr:220 - jr:224).

- **Неиспользуемый код.** Правила jr:205 и jr:206 находят методы и классы, до которых выполнение
  не доходит от точек входа: на них нет вызовов и ссылок либо они есть только из такого же
  неиспользуемого кода. В сообщении указано, откуда идет вызов: `вызывается только из неиспользуемого
  кода (Service.legacy)`. Классы, которые ссылаются только друг на друга, тоже находятся. Точками входа считаются классы и методы с аннотациями
  (`@Service`, `@GetMapping`, `@Scheduled`, `@Bean`), `main`, геттеры и сеттеры, переопределенные методы.
  Вызов, который не удалось сопоставить с конкретным методом, и имя в строке (рефлексия, SpEL)
  засчитываются как использование. Каталоги `test` не проверяются, но вызовы из них учитываются,
  если тесты сканируются. Если проверяется часть проекта или библиотека, чьим кодом пользуются извне,
  эти правила лучше отключить.

Ограничения: порядок операторов учитывается только для локальных переменных (поля и свойства объектов —
по всем присваиваниям метода), вызовы через рефлексию и лямбды, переданные в другие методы, в граф вызовов
не попадают.

## Анализ потока данных

Правила jr:323 – jr:330 не ищут шаблон в коде, а исполняют каждый метод «на бумаге»: вместо настоящих
значений переменных хранится то, что о них известно в данной точке.

| Что известно о значении | Пример |
|---|---|
| `null`, не `null`, может быть `null` | после `String s = null`, после `new`, после `if (flag) s = "a"` |
| диапазон целого числа | после `if (count > 10)` значение `count` лежит в `11 ...` |
| длина массива | после `new int[3]` |
| пуста ли коллекция и есть ли значение в `Optional` | после `new ArrayList<>()`, `list.add(x)`, `if (list.isEmpty())`, `Optional.empty()` |
| что вернет геттер после сеттера | после `user.setName(null)` вызов `user.getName()` вернет `null` |

На развилке (`if`, `switch`, `?:`, `&&`, `||`) каждая ветка исполняется со своим состоянием, уточненным
условием: в ветке `if (x == null)` значение `x` равно `null`, после `if (x == null) return;` — не `null`.
После развилки состояния сливаются. Для Java, где нет `goto`, такой обход по структуре кода равнозначен
обходу графа потока управления.

| Правило | Что находит |
|---|---|
| jr:323 | обращение к переменной, которая в этой точке всегда `null` |
| jr:324 | обращение без проверки к значению, которое равно `null` на одном из путей: переменная или поле заданы только в одной ветке, проверены на `null`, но использованы ниже, остались `null` после `catch` либо после цикла, который не выполнился ни разу, получены из `orElse(null)`, из метода, который может вернуть `null`, либо помечены `@Nullable` |
| jr:325 | в метод передается `null`, а метод обращается к параметру без проверки |
| jr:326 | условие всегда истинно либо всегда ложно: лишняя проверка на `null`, сравнение числа вне его диапазона |
| jr:327 | код, до которого выполнение не доходит из-за такого условия либо метода, который всегда бросает исключение |
| jr:328 | деление на переменную, которая в этой точке всегда равна нулю |
| jr:329 | индекс за границей массива (`i <= arr.length`) и результат `indexOf`, использованный без проверки на `-1` |
| jr:330 | `get()` и `orElseThrow()` у `Optional`, который в этой точке всегда пуст: обычно перепутаны ветки условия |

**Через вызовы** значение проходит по сводке метода. Для каждого метода проекта один раз вычисляется:

- может ли он вернуть `null`;
- к каким параметрам он обращается без проверки;
- какие параметры точно не `null`, если метод вернул управление (`ensure(x)` бросает исключение для `null`);
- возвращает ли он управление вообще (`fail()` всегда бросает исключение);
- для методов-проверок — что они возвращают для `null`: после `if (isBlank(x)) return;` значение `x` не `null`.

Сводка использует сводки вызываемых методов, поэтому длина цепочки вызовов не ограничена. То же известно
о методах библиотек: `Objects.requireNonNull`, `Assert.notNull`, `Objects.isNull` / `nonNull`,
`StringUtils.isBlank` / `hasText`, `CollectionUtils.isEmpty`, `equals`, `orElse(null)`, `indexOf`, `size()`.

Этот справочник лежит в файле `flow-library.properties` внутри приложения: какие методы гарантируют
не-`null`, какие возвращают `true` для `null`, какие не возвращают управление, какие добавляют элемент
в коллекцию и какие только читают объект. Свои методы добавляются отдельным файлом того же вида:

```properties
# app.properties
zond.flow.library=flow-library-extra.properties
```

```properties
# flow-library-extra.properties
asserts-not-null=requirePresent, mustExist
asserts-true=ensureThat
true-for-null=isMissing
never-returns=abort
```

`asserts-true` — методы, после которых условие-аргумент истинно: встроены `checkState`, `checkArgument`
из Guava, `isTrue` и `state` из Spring `Assert`, `isTrue` и `validState` из Commons `Validate`, `verify` из
Guava `Verify`. Первым аргументом должно стоять условие (`x != null`, `!list.isEmpty()`), поэтому
`verify(mock)` из Mockito сюда не попадает.

Записи своего файла добавляются к встроенным. Методы задаются именами без классов.

**Поля своего объекта** (`name` и `this.name`) отслеживаются так же, как локальные переменные:

- после `if (name == null) { log(...); }` обращение `name.length()` — находка;
- `final`-поле, созданное при объявлении (`private final List<X> items = new ArrayList<>()`), не `null`;
- вызов метода своего объекта сбрасывает знания о полях, если по сводке метода не видно, что полей он
  не меняет; вызов метода другого объекта поля не затрагивает;
- поля `volatile` не отслеживаются: их меняют другие потоки;
- в лямбде о полях ничего не известно: она выполнится неизвестно когда.

**Циклы** проходятся несколько раз, пока состояние в начале итерации не перестанет меняться. Оно и
используется для проверки тела и кода после цикла:

- `String last = null; for (...) last = item; last.length()` — находка: цикл мог не выполниться ни разу;
- `previous.length()` в начале тела, когда в конце тела `previous` может стать `null`, — находка для
  второй итерации;
- счетчик после `while (i < 10) i++` не меньше 10;
- граница числа, которая сдвигается от прохода к проходу, сразу отодвигается до предела — иначе счетчик
  рос бы по единице без конца. Если состояние не устоялось за шесть проходов, о переменных,
  которые меняются в цикле, не утверждается ничего.

**Аннотации** — обещания автора кода, они важнее того, что видно в теле:

| Где | `@Nullable`, `@CheckForNull` | `@NonNull`, `@Nonnull` |
|---|---|---|
| параметр | может быть `null` | не `null` |
| поле | может быть `null` и на входе в метод, и после вызова, который мог его изменить | не `null` |
| метод | результат может быть `null` — в том числе у метода интерфейса и у переопределяемого | результат не `null` |

`@NotNull` из Bean Validation гарантией не считается: она проверяется, только когда объект валидируют.

Чтобы не давать ложных находок, анализ намеренно осторожен:

- **Сводка только у методов, которые нельзя переопределить:** `private`, `static`, `final`, методы
  `record` и `enum`, а также методы, у которых в проекте нет тезки с тем же числом параметров.
  Для остальных неизвестно, какое тело выполнится при вызове. На аннотации это не распространяется.
- **Метод, отражающий состояние поля, равносилен геттеру.** Если метод возвращает `null` в ветке
  `if (name == null)`, где `name` — поле, о его результате ничего не утверждается: что лежит в поле,
  вызывающий код знает лучше.
- **Связанные условия понимаются.** Если переменная задана под условием `if (flag)`, под тем же условием
  ниже она не `null`. То же с флагом: `found = true` в той же ветке и `boolean ok = x != null` с
  последующим `if (ok)`.
- **Связи между переменными понимаются.** После `if (a == null && b == null) return;` известно, что `null`
  не обе сразу. Поэтому в ветке `if (a == null)` переменная `b` не `null`, и `b.length()` — не находка.
  То же для `if (a != null || b != null) { ... }` и проверок через `Objects.isNull` / `nonNull`. Связь
  теряет силу, когда одной из переменных присваивают новое значение.
- **Связи через коллекции понимаются.** Если в ветке `if (name == null)` в список ошибок добавили запись,
  а ниже стоит `if (!errors.isEmpty()) return;`, то после него `name` не `null`.
- **Состояние объекта сбрасывается при любом сомнении.** То, что известно о коллекции или объекте,
  забывается, когда у него вызывают метод, не похожий на чтение, передают его в другой метод, в лямбду
  или по ссылке на метод (`items.forEach(result::add)`).
- **Обращение к параметру считается обязательным, только если до него метод не мог завершиться.**
  После `if (other == null) return;` обращение к параметру выполняется не при каждом вызове, поэтому
  передача `null` в такой метод находкой не считается.
- **Повторный вызов считается тем же значением:** после `if (user.getName() != null)` вызов
  `user.getName()` не `null`.
- **О булевых флагах не сообщается:** `boolean debug = false; if (debug)` и `valid = valid && check()`
  пишут нарочно.
- **Тестовые классы пропускаются:** в тестах `null` передают намеренно.

Ограничения:

- Отслеживаются только поля своего объекта, объявленные в этом же классе. Поля других объектов
  (`order.customer`), унаследованные поля, элементы коллекций и массивов не отслеживаются.
- Вызов метода другого объекта считается не меняющим поля своего. Если тот метод получает `this`
  аргументом, поля сбрасываются; обратный вызов иным путем останется незамеченным.
- Цикл, который по смыслу всегда выполняется хотя бы раз (коллекция заведомо не пуста), анализу
  неизвестен: переменная, заданная только в его теле, будет названа возможным `null`.
- Значение, связанное с другим неочевидным способом (`errors.add(...)` в ветке с `null` и
  `if (!errors.isEmpty()) return` ниже), будет названо возможным `null`.
- Аннотации читаются только в исходниках проекта: у методов библиотек из jar-файлов они не видны.
- Исключения прослеживаются только через `try` / `catch`; рефлексия и прокси Spring не учитываются.

## Как добавить свое правило

Правило — это Spring-бин, реализующий интерфейс `Rule`. Регистрировать его нигде не нужно: сканер
получает все такие бины сам.

**1. Заведите код** — следующую по номеру константу в `rules/RuleCodes.java`:

```java
public final static String THREAD_STOP_RULE_CODE = "jr:363";
```

**2. Напишите класс** в подпакете `ru.akvine.zond.rules`, который отвечает типу проблемы: правило с
`ErrorType.CONCURRENCY` кладется в `rules.concurrency`, с `ErrorType.SECURITY` — в `rules.security` и так далее
(см. [Устройство проекта](#устройство-проекта)). Проще всего унаследоваться от `AbstractRule`:
он дает имя правила, сборку находки (`violation(...)`) и чтение порогов.

```java
@Component
public class ThreadStopRule extends AbstractRule {
    private static final String STOP = "stop";
    private static final Set<String> THREAD_TYPES = Set.of("Thread");

    @Override
    public String code() {
        return RuleCodes.THREAD_STOP_RULE_CODE;
    }

    @Override
    public String description() {
        return "Сканирует код и ищет остановку потока через Thread.stop()";
    }

    @Override
    public List<Violation> check(SourceFile sourceFile) {
        return sourceFile.unit().findAll(MethodCallExpr.class).stream()
                .filter(call -> STOP.equals(call.getNameAsString()) && call.getArguments().isEmpty())
                // По типу, а если тип определить не удалось - по имени объекта
                .filter(call -> call.getScope()
                        .filter(scope -> LocalTypes.isAnyOf(scope, THREAD_TYPES,
                                () -> scope.toString().toLowerCase().contains("thread")))
                        .isPresent())
                .map(call -> violation(sourceFile, call,
                        "Thread.stop() обрывает поток в произвольном месте и оставляет данные"
                                + " в несогласованном состоянии; используйте interrupt()"))
                .toList();
    }

    @Override
    public ErrorLevel errorLevel() {
        return ErrorLevel.CRITICAL;
    }

    @Override
    public ErrorType errorType() {
        return ErrorType.CONCURRENCY;
    }
}
```

`sourceFile.unit()` — синтаксическое дерево файла из библиотеки [JavaParser](https://javaparser.org/).

**3. Выберите вид правила**, если проверка по одному файлу не подходит:

| Что проверяется | Что реализовать |
|---|---|
| Один Java-файл | `Rule` (через `AbstractRule`), метод `check(SourceFile)` |
| Проект целиком: связи между классами из разных файлов | `ProjectRule`, метод `checkProject(List<SourceFile>)` |
| Файл настроек `application.properties` / `.yml` | `ConfigRule` (через `AbstractConfigRule`), метод `checkConfig(ConfigFile)` |
| Миграции, файлы сборки, Docker, Kubernetes, CI, настройки логирования, `messages*.properties` либо все сразу: код, настройки и эти файлы | `ContextRule` (через `AbstractContextRule`), метод `checkContext(ScanContext)` |

**4. Пользуйтесь готовыми помощниками** из пакета `rules.support` вместо разбора дерева вручную:

| Помощник | Для чего |
|---|---|
| `LocalTypes` | тип выражения (`typeOf`), проверка на библиотечный тип (`isAnyOf`), поиск объявления переменной |
| `Types` | разрешение типов: предки, аннотации класса, тип из JDK или из проекта |
| `MethodCalls` | вызов вида `Type.method(...)`, имя получателя вызова |
| `Annotations`, `TransactionalAnnotations` | аннотации на классах и методах |
| `SpringBeans`, `Repositories`, `Loggers`, `JpaEntities` | бины, репозитории, логгеры, сущности |
| `Loops`, `StreamChains`, `Nodes` | циклы, цепочки стримов, обход дерева |
| `Lombok` | код, который Lombok создаст при компиляции: геттеры, сеттеры, builder, поле `log` |
| `CallGraph`, `CallChains` | кто кого вызывает в проекте; поиск операции в вызываемых методах |
| `Taint` | доходят ли до выражения данные запроса — через переменные и вызовы между классами |
| `Guards` | стоит ли проверка (`isEmpty()`, `isPresent()`) на пути выполнения к использованию |
| `TestClasses` | находится ли код в тестовом классе |

**5. Сделайте порог настраиваемым**, если он есть. Объявите параметр, верните его из `parameters()`
и читайте через `value(...)` — после этого он задается в `app.properties` и виден в списке правил:

```java
private static final RuleParameter MAX_LINES =
        new RuleParameter("max-lines", 50, "Допустимое число строк в методе");

@Override
public List<RuleParameter> parameters() {
    return List.of(MAX_LINES);
}

// в check(...): if (lines > value(MAX_LINES)) { ... }
```

**6. Напишите тест.** `RuleTests.lines` возвращает номера строк, на которых правило нашло проблемы:

```java
class ThreadStopRuleTest {
    private final ThreadStopRule rule = new ThreadStopRule();

    @Test
    void findsThreadStop() {
        assertThat(RuleTests.lines(rule, """
                class Sample {
                    void run(Thread worker, Timer timer) {
                        worker.stop();
                        worker.interrupt();
                        timer.stop();
                    }
                }
                """)).containsExactly(3);
    }
}
```

Если правилу нужны типы из других файлов, смотрите `TypeAwareRulesTest`: там код загружается так же,
как при настоящем сканировании.

**7. Запустите сборку.** `RuleCatalogConsistencyTest` проверит новое правило вместе с остальными:
код уникален и объявлен в `RuleCodes`, есть описание, уровень и тип, на классе стоит `@Component`.

После сборки стоит прогнать приложение на настоящем проекте и просмотреть находки: ложные срабатывания
на тестовых примерах обычно не видны.
